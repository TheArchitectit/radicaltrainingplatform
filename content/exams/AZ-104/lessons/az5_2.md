# Implement backup and recovery (S5.2)

*Module S5.2 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

Backup and disaster recovery get discussed as one subject, but they answer two different questions, and separating them is the most useful thing this lesson can give you. **Backup** answers "the data is gone or corrupted — put it back the way it was." It is a point-in-time copy, and restoring it takes time. **Site Recovery** answers "the whole workload is unavailable because its region is unavailable — keep the business running." It is replication and failover, not a restore.

Hold those apart and most scenarios resolve themselves: if the ask is about lost or damaged *data*, you are in the backup half; if it is about an unavailable *workload*, you are in the Site Recovery half.

## Vaults: where backups live

A backup is stored in a vault, and two kinds matter.

The **Recovery Services vault** is the older, broader one: backups for virtual machines, file shares, on-premises servers, and SQL databases in Azure VMs.

The **Backup vault** is the newer type, used by newer-generation workloads — notably blob storage backups and Azure Database for PostgreSQL. When a question mentions backing up blobs, the answer is a Backup vault, and that is a reliable tell.

The vault is the container, not the schedule — which brings us to policy.

## Policies, recovery points, and retention

A **backup policy** is a separate object from the vault, defining two things: **frequency** (how often a backup is taken) and **retention** (how long each is kept — daily points for a short window, weekly, monthly, and yearly points for longer). One policy can attach to many resources, and one vault can hold many policies.

Each backup produces a **recovery point**, and choosing a recovery point *is* choosing the restore's point in time. If a question asks how far back you can go, the answer comes from the retention in the policy, not from anything on the VM itself.

## Soft delete and restore options

**Soft delete** keeps backup data for a period after it would otherwise be deleted, so a recovery point removed accidentally — or maliciously — can still be recovered. It is a security control, not just a convenience: an attacker who reaches a vault and deletes backups is trying to destroy your ability to recover, and lengthening soft delete retention is a hardening step.

Restoring a virtual machine offers several shapes, and picking between them is a frequent scenario:

- **Replace the existing VM** — restore over the original disk. Simplest, and most destructive to current state.
- **Restore the disks** — create new disks from the recovery point and attach them, useful when you want to inspect the data before committing.
- **File-level recovery** — mount the recovery point and copy individual files out. The right answer when one folder was deleted and everything else is fine.

**Cross-region restore** restores to a paired region from vault-replicated backup data, covering the case where the primary region is the problem — but it is still a restore, so it is measured in restore time.

## Site Recovery: replication and failover

**Azure Site Recovery** is a different service with a different job. It continuously replicates virtual machines to a secondary region, so that when the primary fails you can run a **failover** and bring the workload up elsewhere. You rehearse it with a **test failover**, which brings up the replica in an isolated network so you can verify it works without disturbing production — "verify the plan without impacting production" means a test failover, not a real one.

The distinction to carry away: Site Recovery has a low recovery time objective because a replica is already warm; backup has a higher one because data must be transferred and rebuilt. Many designs run both.

## Reports and alerts

Backup reports and built-in alerts cover the operational side: are jobs succeeding, are any resources unprotected, is a job overrunning. These matter because a backup job that silently fails is worse than none — cost and false confidence without the protection.

## Worked example: picking the mechanism

1. **A user deleted a folder from a file share; everything else is intact.** Use **file-level recovery**. Replacing the whole share would discard correct changes made since that recovery point for no reason.
2. **A VM's OS disk was corrupted by a bad update an hour ago.** Restore from a **recovery point taken before the update**, replacing the VM or restoring the disks. The question is which point predates the damage; how far back you can reach is bounded by the policy's retention.
3. **The finance application must keep running if the primary region fails.** This is workload continuity, so use **Site Recovery** with replication to a secondary region. Backup would restore the data eventually, but the requirement is availability.
