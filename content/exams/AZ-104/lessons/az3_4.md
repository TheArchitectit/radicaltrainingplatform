# Create and configure Azure App Service (S3.4)

*Module S3.4 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

App Service hosts a web application without asking you to manage a server. The mental picture that makes the whole service legible is a **separation between the app and the compute it runs on**: the app is the thing you deploy, and the plan is the machine underneath it. Nearly every confusing question about tiers, scaling, and slots resolves once you can say which of the two you are changing.

## The plan is the compute; the app is the workload

An **App Service plan** defines a region, a pricing tier, a VM size, and a number of instances, and every app placed in that plan shares those resources. This is why the first design question is never "which tier is best" but "which apps can afford to share a machine". Two apps in one plan compete for the same CPU and memory, and a burst of traffic in one is felt by the other. The app itself carries the deployment — code or a container image — plus its settings, custom domains, and slots.

## Tiers, and what each one unlocks

- **Free and Shared** — the lowest tiers, suited to experiments. Limited compute and no custom domain of your own.
- **Basic** — dedicated compute, custom domains, and manual scaling to more instances.
- **Standard** — adds what a real release process needs: **deployment slots**, **autoscale**, and **backup**.
- **Premium** — more performance and instances, larger slot counts, and additional networking and resilience options.
- **Isolated** — runs in a dedicated environment, for the strictest network isolation requirements.

The tiers are cumulative, so the practical reading is: if a requirement mentions slots, autoscale, or backup, the tier must be Standard or above.

## Scaling up and scaling out

Two different actions share the word "scale":

- **Scale up** means moving to a larger VM size in the plan — a bigger machine. It usually requires a change that restarts the app.
- **Scale out** means adding instances of the same size, and it is the action **autoscale** performs against a metric such as CPU or a schedule.

Scale out is the usual answer to variable load because it can be added and removed without changing the shape of the machine.

## Slots and swap

A **deployment slot** is a second, fully addressable instance of the same app inside the same plan. The standard pattern is to deploy to a non-production slot, let it warm up, verify it, and then **swap** it into production. The swap exchanges the content of the two slots, so the release happens as an exchange rather than as a period of downtime. Some settings are marked as slot settings and stay with the slot rather than travelling with the swap — connection strings are the classic example, and getting this wrong is the usual cause of an app that works in staging and fails immediately after a swap.

## Domains, certificates, backup, and networking

- **Custom DNS names** — you map your own hostname to the app by creating the DNS records the service asks for.
- **TLS certificates** — a managed certificate can be issued and renewed for you, or you can bring your own and bind it to the hostname.
- **Backup** — at Standard and above, a scheduled backup of the app's content and configuration can be written to a storage account and restored.
- **Access restrictions** — inbound rules that allow or deny traffic by address or range, evaluated before the request reaches the app.
- **VNet integration** — gives the app outbound access into a virtual network, so it can reach a database that is not exposed publicly.
- **Private endpoints** — the opposite direction: a private inbound address inside a virtual network rather than a public one.

## App Service and containers

App Service can also run your application from a container image instead of a code deployment. You gain the ability to package the runtime exactly as you want, and you give up the fully managed runtime that patches itself. The plan, the tiers, the slots, and the networking rules work the same way either way.

## Worked example: reading a requirement

1. A release must be verified in a warm environment and then go live with no downtime. **Deploy to a slot, verify, then swap.**
2. An app must reach a database that has no public endpoint. **VNet integration for outbound access**, with a private endpoint on the database side.
3. Traffic varies sharply through the day and the app must follow it. **Scale out with autoscale rules**, which requires Standard or above.
4. A connection string must not follow a swap into production. **Mark it as a slot setting**, so the value stays with the slot.
