# Configure name resolution and load balancing (S4.3)

*Module S4.3 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

This lesson covers the two services that sit in front of everything else you have built. Name resolution turns a name into an address, and load balancing turns one address into many servers. The mental picture: **Azure DNS** answers "which address?", and a **load balancer or application gateway** answers "which server, and is it healthy?"

## Azure DNS zones

Azure DNS hosts two kinds of zone.

A **public zone** hosts records for a name you own and answers queries from the internet. You create the zone, then take the name server records Azure assigns you and set them at your domain registrar so the world can find your zone.

A **private zone** answers queries only from the virtual networks you link to it. You create the zone (for example `internal.contoso.com`), then add **virtual network links**. Two details matter:

- **Auto-registration** can be enabled on a link, and Azure then creates and updates an A record for each VM in the linked VNet automatically as VMs are created, started and deleted. Auto-registration is a per-link setting.
- A VM must be linked to the zone to use it. A private zone linked only to VNet A does not answer for a VM in VNet B unless you link B as well.

Common record types are **A** (name to IPv4), **AAAA** (name to IPv6), **CNAME** (name to another name), **MX** and **TXT** for mail and verification, and **SRV** for service locations. By default, Azure provides name resolution to VMs in a VNet automatically, but if you set **custom DNS servers** on the VNet, you replace that service — the custom servers must then resolve everything the VMs need, including Azure service names.

## Choosing a load balancing service

The first question is which layer you are balancing at.

- **Azure Load Balancer** works at **Layer 4** — TCP and UDP. It cannot see a URL, a host header or a cookie. It is fast, cheap, and right for any non-HTTP protocol or when you only need to spread connections.
- **Application Gateway** works at **Layer 7** — HTTP and HTTPS. Because it reads the request, it can route by path or host name, terminate TLS, and provide a web application firewall.

Either can be **public** (a public frontend IP, for internet clients) or **internal** (a private frontend IP, for clients inside your network).

An Azure Load Balancer has three pieces worth separating:

- the **frontend IP configuration** — the address clients connect to
- the **backend pool** — the set of VMs or instances that receive traffic
- the **health probe** — a periodic check (protocol, port, interval) that decides whether an instance is eligible to receive traffic

The probe and the pool are different things, and that distinction explains most load balancing failures: a server can be correctly listed in the backend pool and still receive no traffic because its health probe is failing.

## Worked example: three load balancing faults

1. **A Standard load balancer has three VMs in its backend pool, but all traffic lands on one VM.** Look at backend health. The other two are almost certainly failing the probe — commonly because the probe is set to a port or path the application does not answer on.
2. **Backend health shows every instance as unhealthy even though the application responds from inside the VM.** The NSG is blocking the probe. Health probes originate from the address `168.63.129.16`, so the NSG must allow that source on the probe port. This is the single most common cause of an all-unhealthy pool.
3. **A team needs `app.contoso.com/api` routed to one pool and everything else to another.** That is a path-based decision, so a Layer 4 load balancer cannot do it. Use Application Gateway with path-based routing rules.
