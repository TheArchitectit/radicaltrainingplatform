# Configure access to storage (S2.1)

*Module S2.1 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

Almost every question about storage access is the same question: who may reach this data, and what proof do they present? The mental picture to build is a storage account you unlock with a shared secret, a signed token, or an identity — with the network around it narrowing who can even try.

## Access keys

Every storage account is created with two **access keys**, key1 and key2. An access key is a shared secret: anything that presents it can do anything in the account. That bluntness is why two keys exist — regenerate key2, move every application to it, then regenerate key1 once nothing depends on the old value. With one key, every rotation would be a hard cutover.

## Shared access signatures

A **shared access signature (SAS)** is a signed token appended to a storage URL, carrying permissions, a start and expiry time, and the resources it applies to. Anyone holding the URL has exactly the access the token describes — no more. Three kinds matter:

- A **service SAS** secures access to one service in the account, such as Blob or File.
- An **account SAS** can cover several services at once, plus some account-level operations.
- A **user delegation SAS** is signed with **Microsoft Entra ID** credentials instead of an access key: the client asks Entra ID for a user delegation key and builds the SAS from that. Because no account key is involved, prefer this form for blob access from your own code — and because the signature traces back to a user, removing that user's permissions stops the token working.

## Stored access policies

The awkward part of a SAS is that once you hand it out you cannot edit it. To make one revocable and adjustable, define a **stored access policy** on the container and have the SAS reference that policy by name instead of spelling out its own start, expiry, and permissions. Changing the policy changes every SAS tied to it; deleting the policy revokes them all at once. Stored access policies pair with service SAS tokens, not with account or user delegation SAS.

## Network controls

Keys and tokens decide *who* gets in; the **storage firewall** decides *from where*. Accounts accept connections from all networks by default. Switch to selected networks and add **virtual network rules** (which rely on **service endpoints** to let specific subnets through) or **IP rules** for known public addresses.

A **service endpoint** keeps traffic on the Azure backbone, but the account still has a public endpoint — you are only restricting who may use it. A **private endpoint** places a private IP address from your subnet in front of the account instead, so traffic never uses the public endpoint at all. Choose it when public access must be switched off entirely; it also serves on-premises clients over VPN or ExpressRoute.

## Identity-based access for Azure Files

Azure Files can also be reached with a user identity rather than a key or token. That requires the storage account to be joined to a directory — either your on-premises **Active Directory Domain Services** (which needs connectivity to the domain controllers) or **Microsoft Entra Domain Services**. Once joined, share-level permissions are granted to identities and users authenticate much as they would to a file server.

## Worked example: a partner needs nightly upload access

1. A partner application must write blobs to one container for 30 days and nothing else. Send an access key? No — it would let them read and delete everything in the account. Issue a SAS scoped to that container with write permission and a 30-day expiry.
2. The partner warns the window may need extending. Rather than issuing a fresh SAS, attach a stored access policy to the container and issue the SAS against it, so you can adjust the expiry later — or delete the policy to revoke access immediately.
3. Your own application then needs the same container. Prefer a user delegation SAS or a managed identity, so no account key is stored in the application.
