# Automate deployment with ARM templates or Bicep files (S3.1)

*Module S3.1 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

Section 3 is about compute, and this first lesson is about the way compute gets created. Before you learn what a virtual machine needs, it helps to see the shape of the thing that asks for it. This lesson builds one mental picture: **a deployment is a document that describes the end state you want, and Azure works out the steps to reach it.**

## Declarative versus imperative

An **imperative** instruction is a list of steps: create a network, then create a NIC, then create the VM. A **declarative** instruction describes the finished picture and lets the platform decide how to get there. ARM templates and Bicep files are declarative: you write down the resources you want and how they relate, and the deployment engine orders the work.

That difference matters most when you run the same deployment a second time. A script that says "create a VM" will fail or duplicate work if the VM already exists. A template that says "this VM should exist with these settings" is **idempotent** — running it again produces the same end state rather than a second VM.

## The anatomy of an ARM template

An ARM template is JSON with a small, fixed set of top-level sections. You will not memorise syntax, but you should recognise each part and know why it exists:

- **`$schema`** — tells the deployment tooling which template language version to read the file as. If the schema is wrong or missing, the tooling cannot parse the file, so it is the first thing to check when a template is rejected before anything is even attempted.
- **`contentVersion`** — your own version label for the template, so you can tell one revision of your file from another. It is authoring metadata; Azure does not act on the number.
- **`parameters`** — the inputs supplied at deployment time, such as a name, a region, or an administrator login. Parameters are what make one template reusable across environments.
- **`variables`** — values computed inside the template, so a repeated string or a derived name is written once.
- **`resources`** — the actual things to create, each with a **type**, a **name**, a **location**, and an **`apiVersion`**. The `apiVersion` selects which version of the resource provider's API handles that resource, and it is how a template written years ago keeps behaving the way it did.
- **`outputs`** — values handed back after the deployment finishes, such as a generated hostname you want to feed into the next step.

## Bicep: same destination, cleaner road

**Bicep** is a language with terser syntax for exactly the same job. Where JSON needs nested brackets and repeated property names, Bicep uses short declarations and automatic dependency inference. The important fact is that Bicep is not a second deployment system: it **transpiles to ARM JSON**, so the engine underneath is identical. Choose Bicep for readability; nothing about the deployed result changes.

## Modes, what-if, and the deployment as a record

Two settings govern how a deployment reconciles what you asked for against what exists:

- **Incremental** (the default) adds and updates the resources in the template and leaves everything else in the resource group alone.
- **Complete** additionally removes resources that are in the resource group but absent from the template. That is a real deletion, so it is not a mode to leave switched on by accident.

Because the engine can see both sides, it can tell you what it *would* change before it changes anything. **What-if** produces that preview: which resources will be created, modified, or deleted. Read it whenever a deployment touches something that already carries data.

Finally, Azure keeps a **deployment history** on the scope you deployed to, recording the template and the parameters used. This is why administrators say the deployment is the record: the history explains how a resource group reached its current state, and it can be reviewed or exported as a template.

## Worked example: the resource group with a surprise

1. You inherit a resource group containing a VM, a storage account, and a network. You are asked to redeploy an updated template that describes only the VM. **Incremental mode.** The template adds nothing about the storage account, so the storage account stays. In complete mode, that same deployment would delete it.
2. A template fails immediately with a parse error and no resources are attempted. **Check `$schema` first.** A malformed or mismatched schema stops the tooling before any resource provider is contacted.
3. You must change a template that manages a production database. **Run what-if.** The preview shows whether the database will be modified or deleted, which is exactly the information you need before committing.
