# Provision and manage containers (S3.3)

*Module S3.3 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

A container packages an application with everything it needs to run, and shares the host's operating system kernel instead of carrying its own. That single fact is the source of everything else in this lesson: containers start in seconds, they are small, and they need somewhere to run. The mental picture is a **ladder of how much platform you are willing to manage** — from a registry that stores images, to a service that runs one container, to a service that runs a whole application.

## The registry: where images live

**Azure Container Registry (ACR)** is a private place to store and distribute container images. It exists because a container service needs to pull an image from somewhere it trusts. ACR supports authentication integrated with your directory, so a container service can pull without credentials being pasted into a configuration file, and higher tiers add features such as geo-replication so pulls are served from a nearby region.

The registry does not run anything. It stores images and serves them.

## Azure Container Instances: the fastest way to run one thing

**Azure Container Instances (ACI)** runs a container with no cluster, no nodes, and no orchestrator to maintain. It is billed by the second for the resources the container uses. The unit of deployment is the **container group** — one or more containers that are scheduled together on the same host and share a lifecycle and a network space, much like a single pod.

ACI is the right tool when the job is simple and short-lived: a batch task, a build step, an isolated piece of work, or a first experiment with an image. What it does not give you is an application platform. There is no built-in revisioning, no traffic splitting, and no scale-to-zero behaviour driven by demand.

## Azure Container Apps: a platform for applications

**Azure Container Apps** sits a rung higher. It is serverless in the sense that you do not manage nodes, but it provides the features an application actually needs:

- **Scale to zero** — when no requests arrive, the app scales down to nothing and you stop paying for compute.
- **Revisions** — each deployment of a changed container produces an immutable revision, and you can send traffic to a specific revision or split traffic between them. This is how a canary release works without a second environment.
- **Event-driven scaling** — scaling rules can follow HTTP concurrency, or external event sources such as a queue's depth, so the app grows in response to the work waiting for it rather than only to CPU.
- **Ingress** — an HTTPS endpoint, with certificates handled for you.

The clean distinction: **ACI runs a container group; Container Apps runs an application.** If you need revisions, traffic splitting, or scale to zero, ACI is the wrong rung of the ladder.

## Sizing and scaling rules

Both services ask for CPU and memory, but they ask differently. In ACI you allocate CPU and memory to the containers in the group, and that allocation is the capacity the group gets. In Container Apps you set CPU and memory per replica and then describe the **scaling rule**: the minimum and maximum number of replicas, and the condition that adds or removes them. Setting a minimum of zero is what enables scale to zero; setting a minimum of one keeps a warm instance and avoids the cold start.

## Worked example: choosing the rung

1. A nightly job converts files and takes about four minutes. It needs no endpoint and nothing after it finishes. **ACI.** A short-lived single task with no orchestration need is exactly what it is for.
2. An API must cost nothing overnight, then absorb a morning spike driven by a queue. **Container Apps with a scale-to-zero minimum and an event-driven rule.** Scale to zero plus queue-based scaling is the combination ACI cannot express.
3. A new release must reach ten percent of users before everyone else. **Container Apps revisions with traffic splitting.** Sending a share of traffic to a specific revision is a platform feature, not something a single container group can do.
