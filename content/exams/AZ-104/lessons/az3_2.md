# Create and configure virtual machines (S3.2)

*Module S3.2 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

A virtual machine is the resource where the most decisions meet: what software it starts from, how much machine it gets, where it lives, and how it survives a failure. The mental picture for this lesson is a **stack of coupled choices** — you rarely change one without touching another, and knowing which pairs are locked together is what turns a failed change into a planned one.

## The inputs you choose at creation

Every VM creation asks the same core questions:

- **Image** — the starting operating system and any preinstalled software. The image decides which sizes and which extensions are valid.
- **Size** — the CPU, memory, and local temporary storage the VM receives.
- **Region** — the datacentre location, which also determines which sizes and which zones are available, so region is chosen early.
- **Networking** — the virtual network, subnet, and network interface. A VM without a NIC in a reachable subnet is running but unreachable.

Sizes come in **families**, grouped by workload shape: the **B series** for burstable general work, the **D series** for balanced general purpose, the **E series** for memory-heavy workloads, the **F series** for compute-heavy work, and the **N series** for GPU workloads. Choosing a family is a statement about the workload, not just about budget.

## Resizing, and why deallocation appears

A VM runs on a physical host that must have capacity for its size. If you ask for a size the current host cannot provide — a different family, or a larger shape — the VM must be **deallocated** first so it can be placed on suitable hardware. A resize within the same family and host often succeeds live. This is the first place the coupling shows: size changes are not always online operations.

## Disks

A VM has an **OS disk**, which holds the operating system, and zero or more **data disks** attached for additional storage. These are **managed disks** — Azure owns the storage account behind them, so you manage the disk, not the account. The tiers trade cost against performance:

- **Standard HDD** — cheapest, lowest throughput, fine for backups and infrequent access.
- **Standard SSD** — a middle tier for light production workloads.
- **Premium SSD** — higher throughput and lower latency, the common production choice.
- **Ultra Disk** — the highest performance tier, for the most demanding workloads.

A disk's tier can be changed later, but not every change is available on every disk, so the tier is worth choosing deliberately at creation.

## Availability: sets, zones, and scale sets

If a VM matters, the question is what happens when hardware or a platform update takes it away.

- An **availability set** spreads VMs across **fault domains** (separate physical groupings that share power and networking) and **update domains** (groups rebooted together during maintenance). It protects against a single rack or a single maintenance wave, but all members stay in one datacentre.
- **Availability zones** are physically separate datacentres inside a region, so placing VMs across zones survives the loss of an entire datacentre, which an availability set cannot.
- A **virtual machine scale set (VMSS)** manages a group of identical VMs from one definition, so a change to the image or size applies to every instance. Scale sets support **autoscale** rules that add instances when a metric such as CPU rises and remove them when it falls.

## Moving, stopping, and extending

A VM can be moved between resource groups and between subscriptions, but the move takes its dependencies along — disks and network interfaces travel with it — and some attached resources block the move until they are handled. Moving to a *different region* is not a move at all; it is a rebuild.

**Stopping** deserves care. Deallocating a VM releases the compute and stops the compute charge. Shutting the operating system down from inside leaves the VM stopped but still allocated: the compute is still reserved and still billed.

**Extensions** are small agents installed into a VM to do a job: monitoring, configuration management, or running a script. The **custom script extension** downloads and runs a script on the VM, which is how a template finishes configuring a machine after the operating system is in place. **Encryption at host** is a VM-level setting that encrypts the temporary disk and the disk caches on the host itself, complementing the encryption already applied to the managed disks.

## Worked example: three requests, three answers

1. A VM resize from a general-purpose size to a much larger memory-optimised size is refused. **Deallocate first.** The current host cannot host the new size, so the VM must be released before it can be placed elsewhere.
2. A workload must survive the loss of an entire datacentre. **Availability zones.** An availability set only spreads across racks and maintenance groups inside one datacentre.
3. A web tier must grow automatically as load rises. **A scale set with autoscale rules.** A fixed set of standalone VMs has no definition to scale from.
