# Configure Azure Files and Azure Blob Storage (S2.3)

*Module S2.3 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

This lesson goes inside the account. The mental picture is a container of objects, each object written in one of three shapes, sitting in one of four access tiers — plus a parallel world of file shares that look like a network drive and can be extended back to a server on your own network.

## Blob types

A blob's **type** is fixed when it is created and follows from how it is written and read:

- **Block blobs** are built from blocks and are the general-purpose choice for text, images, documents, and streaming — most blobs are block blobs.
- **Append blobs** can only be appended to, never overwritten in place, which makes them the natural fit for log and telemetry streams.
- **Page blobs** are organised in 512-byte pages for random reads and writes. They exist mainly to back virtual machine disks, and premium page blobs are the SSD-backed variant.

## Containers and access tiers

A **container** is the grouping inside a blob account; a blob belongs to exactly one container, and container names must be lowercase and URL-safe. Inside a container, each blob sits in an **access tier** that trades storage cost against access cost and latency:

- **Hot** — for data read often. Highest storage cost, lowest access cost.
- **Cool** — for data read occasionally, with a 30-day minimum before early-deletion charges apply.
- **Cold** — for data read rarely, with a longer minimum.
- **Archive** — for data that may never be read again. Cheapest to store, most expensive and slowest to read.

An archived blob is **offline**: it cannot be read at all until it is **rehydrated** to hot or cool, and standard-priority rehydration takes hours. Moving a blob out of archive is that rehydration — there is no instant switch.

## Lifecycle management, versioning, and soft delete

**Lifecycle management** rules act on conditions you define, such as days since a blob was last modified or last accessed, and either move blobs to a cooler tier or delete them — including old versions and snapshots. They are how tiers are used in practice rather than by hand.

**Blob versioning** keeps the previous contents of a blob each time it is overwritten or deleted, so you can read or promote an earlier version. **Soft delete** keeps deleted blobs, containers, or file shares recoverable for a retention period you set, which is the first place to look when someone deletes something by mistake. **Snapshots** are read-only point-in-time copies of a blob or a file share.

## Azure Files

**Azure Files** offers managed SMB and NFS shares. A share has a **tier** that sets its performance and cost profile, and a **quota** that caps how large the share may grow. **Azure File Sync** bridges a share to Windows Servers on your network: an agent on each server keeps a local folder in step with the Azure share, and **cloud tiering** can leave frequently used files on local disk while the rest stay in Azure as placeholders, which keeps the local volume small.

## Worked example: reducing storage cost without losing data

1. A team's diagnostic logs are written continuously and never modified. Append blobs are the right shape, since the writer only ever adds to the end.
2. The logs are read heavily for a week and then almost never. A lifecycle rule moves them from hot to cool after 30 days and to archive after 180 — after which a rehydration is required before anyone can read them, and that takes hours, so the rule should not archive anything still under investigation.
3. A developer deletes a container by mistake. Soft delete on the container is what allows recovery within the retention window; versioning alone would not bring the container back.
