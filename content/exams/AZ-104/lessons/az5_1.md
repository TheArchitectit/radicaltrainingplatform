# Monitor resources in Azure (S5.1)

*Module S5.1 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

Monitoring gets easier once you separate two questions people blur together: *what is the resource doing right now?* and *who changed it?* Azure Monitor answers both, with different stores of data. **Metrics** describe behaviour and performance. The **activity log** records control-plane operations — the create, update, and delete actions taken against your resources. Most monitoring decisions start with picking the right one.

The second mental picture is a pipeline: signal → condition → action. An alert rule is that pipeline made explicit.

## Metrics, and where they come from

**Metrics** are numeric time-series values: lightweight, retained for a bounded period, queryable near-real-time. Azure separates **platform metrics**, which every resource emits automatically, from **guest metrics**, which come from inside a virtual machine's operating system — memory in use, or free space on a volume.

That explains a common complaint: "the CPU chart works, but there is no memory chart." CPU percentage is a platform metric the hypervisor can see; memory pressure inside the guest is invisible unless an agent in the VM reports it — the job of the Azure Monitor Agent and VM insights. When an expected metric is missing, ask whether it is a guest metric and whether the agent is healthy.

## Activity log, resource logs, and diagnostic settings

The **activity log** is a subscription-level record of control-plane operations: who created, modified, or deleted what, and when. If a resource changed unexpectedly, this is where you look for the change itself. It will not tell you the resource is slow.

**Resource logs** are different: the resource emits them (detailed request records from a storage account or key vault, say) and nothing collects them by default. You route them with **diagnostic settings**, choosing a destination:

- a **Log Analytics workspace**, for querying alongside other data,
- a **storage account**, for cheap long-term archival,
- **Event Hubs**, for streaming to an external system.

A diagnostic setting is a routing decision, not a storage decision — the same log can go to several destinations at once.

## Log Analytics and KQL

A **Log Analytics workspace** is the query engine and store for log data, queried with **KQL**: a table name, then operators separated by pipes, typically filtering rows, projecting columns, and aggregating or sorting. You need not memorise operators — just recognise that "query logs across many resources from one place" points at a workspace, and that a workspace is what alert rules on log data are built against.

## Alerts: signal, condition, action

An **alert rule** has three parts. The **signal** is the metric or log query being watched. The **condition** is the threshold and evaluation frequency — average CPU above a value for five minutes, say. The **action group** is what happens when the condition is met: email, SMS, voice call, push, webhook, runbook, or Logic App.

An **action group** is reusable, which is the point of separating it: define "notify the platform team" once and attach it to many rules. **Alert processing rules** sit on top, suppressing or rerouting notifications — muting alerts during a maintenance window without disabling the rules themselves.

## Insights and Network Watcher

**Azure Monitor Insights** are curated views built on the raw data: VM insights for a fleet of machines, plus insights for storage, networks, and containers, so you need not build the first dashboard yourself.

For networking, **Network Watcher** is a regional service of diagnostic tools — IP flow verify, next hop, packet capture, connection troubleshoot. **Connection Monitor** extends this into continuous monitoring of reachability and latency, which is what you want when a problem is intermittent rather than reproducible on demand.

## Worked example: choosing the right tool

1. **A storage account's settings changed overnight and nobody admits to it.** Look at the **activity log**: a configuration change is a control-plane operation, so the log holds the caller identity, operation name, and timestamp. Metrics show that requests behaved differently, not who changed the setting.
2. **A VM has a CPU chart but no memory chart.** The missing value is a **guest metric**. Check that the Azure Monitor Agent is installed and reporting; platform metrics alone cannot see inside the operating system.
3. **The team wants a page when an error appears in an application log, and a ticket outside business hours.** The signal is a **log query in a Log Analytics workspace**. One rule fires both; **alert processing rules** route by time window, so the after-hours path is a routing concern, not a second rule.

## Where this leads
