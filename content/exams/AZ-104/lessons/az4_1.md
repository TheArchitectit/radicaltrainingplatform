# Configure and manage virtual networks in Azure (S4.1)

*Module S4.1 — Azure Administrator AZ-104 study track. Independent study material — see the disclaimer at the end.*

A virtual network in Azure is your own private address space inside a Microsoft region. The single mental picture to hold: a **virtual network (VNet)** is a container of address space, **subnets** are slices of that space, and everything that talks over IP lives in a subnet. When something cannot reach something else, you are almost always asking one of two questions — is the address space laid out correctly, or is there a route that sends the traffic somewhere unexpected?

## Address space, subnets, and reserved addresses

A VNet is defined by one or more **address space** ranges written in CIDR notation, such as `10.0.0.0/16`. Subnets must fall inside that space and must not overlap each other. You can add address space later, but you cannot shrink it, and a subnet cannot be resized while resources are attached to it.

Azure **reserves five addresses** in every subnet, so a `/24` gives you 251 usable addresses rather than 256:

- the first address (`x.x.x.0`) — the network address
- the second (`x.x.x.1`) — the default gateway for the subnet
- the third and fourth (`x.x.x.2`, `x.x.x.3`) — reserved for Azure DNS mapping
- the last address — the broadcast address

Subnets also have special-purpose names you will meet. A **GatewaySubnet** hosts a VPN or ExpressRoute gateway and must be named exactly that. A **AzureFirewallSubnet** hosts Azure Firewall. Getting these names wrong is a classic reason a gateway deployment fails.

## Peering, public IPs, and routes

**VNet peering** connects two VNets so traffic flows over the Microsoft backbone rather than the internet. Peering can be **regional** (same region) or **global** (different regions). Two facts drive most questions:

- Peering is **non-transitive**. If A is peered to B and B is peered to C, A still cannot reach C. You need a direct peering or a gateway in the middle.
- Peering must be created **from both sides**. A peering link created on VNet A shows as *Initiated* until the matching link is created on VNet B; only then does it become *Connected*.

**Public IP addresses** come in two SKUs. **Basic** is the older SKU; it is open by default and pairs with a network security group you must remember to attach. **Standard** is the current SKU: it is **secure by default** (closed to inbound traffic until an NSG explicitly allows it), supports availability zones, and is required for a Standard load balancer. Each public IP is either **static** (the address never changes) or **dynamic**.

**User-defined routes (UDRs)** let you override Azure's automatic routing. Each route has an address prefix and a **next hop type** — common ones are *Virtual network gateway*, *Virtual network*, *Internet*, *Virtual appliance* (a firewall or router NIC), and *None* (drop the traffic). Route precedence, from strongest to weakest, is **UDR, then system route, then BGP route** learned from a gateway.

## Worked example: the VM that cannot be reached

1. **A web server in subnet `10.0.1.0/24` has a Standard public IP but nobody can connect on port 443.** You check the NSG and there is no rule for 443. Because Standard SKU public IPs are secure by default, the missing allow rule is the whole story — add an inbound rule permitting TCP 443 from the internet. On a Basic public IP the same VM would have been reachable.
2. **Two VNets, `Hub` and `Spoke`, are peered. A VM in `Spoke` still cannot reach a VM in a third VNet that is peered only to `Hub`.** Peering is non-transitive, so the Spoke-to-third-VNet path does not exist. Either peer them directly, or route through a firewall or gateway in the hub.
3. **Traffic from a subnet is being inspected by a firewall appliance at `10.0.2.4`, but the firewall sees no traffic.** Add a UDR on the subnet with the destination prefix you care about and next hop **Virtual appliance** set to that IP. A UDR beats the system route, which is why it can redirect traffic that was previously flowing straight out.

## Troubleshooting tools

Three built-in tools answer "why can't this flow?" without guesswork. **IP flow verify** takes a source, destination, port and protocol and tells you whether a packet is allowed or denied, and which NSG rule decided it. **Next hop** shows the effective next hop type for traffic leaving a VM toward a given address. **Connection troubleshoot** runs an end-to-end check between a source and a destination and reports where the path fails.
