# Networking Concepts (N1)

*Module N1 — CompTIA Network+ study track. Independent study material — see the disclaimer at the end.*

Networks are conventions that many different devices agree to follow. This lesson is the vocabulary pass: how to think in layers, what ports and protocols actually are, why IPv4 addressing and subnetting exist, how DNS and DHCP work at Network+ depth, and where the physical media and cloud concepts fit. The A+ networking lesson (A2) already covered the four settings every host needs; here those same ideas are revisited as a *path* a packet takes, not just as fields on a configuration panel.

## The layered model as a mailing analogy

The OSI model is seven layers tall, but a beginner only needs four ideas to read a diagram without getting lost:

1. **Physical (Layer 1)** — the wire, the fiber, the radio wave. Envelope in the truck.
2. **Data link (Layer 2)** — frames on one local link, addressed by MAC, moved by switches. The local mail carrier walking a street.
3. **Network (Layer 3)** — packets between different subnets, addressed by IP, moved by routers. The address that decides which town the letter goes to.
4. **Transport (Layer 4)** — TCP and UDP segments, ports, delivery guarantees (or the lack of them). Whether the letter is registered mail or a postcard.

Higher layers (session, presentation, application) matter for application design; for network troubleshooting, most symptoms live in layers 1–4. When a user says "the website is down," your job is to decide *which layer* is actually lying — cable, local frame, routed path, or service port.

The TCP/IP model collapses this into four (link, internet, transport, application). Same physics, different names. Learn one well and the other is a translation.

## Protocols and ports as agreed conventions

An IP address gets a packet to the right *machine*. A **port** gets it to the right *service* on that machine. There is no cleverness here — clients and servers simply agree in advance that web traffic is 80/443, DNS is 53, SSH is 22, DHCP is 67/68, and so on. If one side changes the convention without the other, the packets arrive and nobody answers.

Useful habit: when a symptom is "the host pings but the application fails," you are almost certainly above Layer 3 and looking at a port, a service, or a TLS/name problem — not at cabling.

## IPv4 addressing and why subnetting exists

An IPv4 address is a 32-bit number written in four octets. The **subnet mask** (often written `/24` instead of `255.255.255.0`) cuts that number into a network part and a host part. The cut is what lets a host decide:

- destination is **on my street** (same network) → deliver directly on the local link;
- destination is **in another town** (different network) → hand the packet to the default gateway.

That single decision is why a wrong mask and a wrong gateway produce such different (and such recognizable) symptoms.

**Subnetting** is the deliberate use of that cut to break one large block into smaller blocks. The reason is mostly *broadcast and operational*: one flat subnet with hundreds of hosts means every ARP and broadcast hits every interface. Smaller subnets limit who hears what, make access control easier, and give you room to grow without a flag day. You do not need to do binary by hand in this beginner pack — you do need to know *why* the boundary exists.

## DNS and DHCP at Network+ depth

A+ teaches what these services hand out. Network+ asks you to follow the path.

### DHCP lease lifecycle

A DHCP lease is not "an IP appears." It is a timed agreement, classically described as **DORA**:

1. **Discover** — the client broadcasts, looking for a server.
2. **Offer** — a server proposes an address and options (mask, gateway, DNS, lease time).
3. **Request** — the client asks for that proposal (important when several servers answered).
4. **Acknowledge** — the server confirms; the lease timer starts.

Later, the client **renews** at T1 (half the lease, usually unicast to the original server) and **rebinds** at T2 (broadcast, any server) before the lease actually expires. A brief periodic dropout is often a renewal-path failure: renew fails, rebind fails, the address is released, and a fresh DORA has to run. That symptom is different from "never got a lease at all" (APIPA on many hosts) and different from "got a lease but the gateway is wrong."

### DNS resolution path

When a client needs `www.example.com`:

1. Check the **stub resolver cache** (and the hosts file, if present).
2. Ask the **configured recursive DNS server**.
3. That server walks the hierarchy (root → TLD → authoritative) or uses cached answers.
4. The client receives an address record and opens a connection to that address.

The classic split of symptoms follows directly:

- **IP works, name fails** → the network path is fine; the translation step is broken (resolver setting, resolver down, or the name itself).
- **Nothing works, name and IP** → you are not in the name layer; look at addressing, gateway, or the remote path.
- **Internal names work, external names fail** → the resolver can answer from its own zone/forwarders path or not; this is a resolver/upstream question, not "DNS is just broken."

This is the same idea as A+ A2's "works by IP but not by name," walked one level deeper into *why* the two cases separate so cleanly.

## Media types, briefly

- **Copper (twisted pair)** — cheap, common, distance-limited (~100 m), sensitive to EMI; category matters for throughput.
- **Fiber** — long distance, immune to electrical noise, higher install skill and cost.
- **Wireless** — flexible placement, shared medium, needs channel/power/security design.

Choosing media is usually a constraint question (distance, interference, existing plant, bandwidth) rather than a taste question.

## Cloud and modern environments at concept level

For this track, cloud is a *connectivity* idea: workloads may sit on someone else's data center, reachable over private links, VPNs, or the public internet. You still need addressing, name resolution, segmentation, and monitoring — the players are just less physical. SDN and similar phrases are "control of forwarding is programmable rather than only console-typed." Know what they change in the mental model; deep product configuration is out of scope here.

## Scenario walkthrough: the failed client

A user says "nothing loads." Walk the path instead of guessing:

1. **Identify** — what exactly fails? A name, a URL, one site, everything?
2. **Local link** — does the host have a sane IP, mask, gateway (compare to a working neighbor)?
3. **Local vs remote** — can you ping a host on the same subnet? The gateway? An external IP?
4. **Name layer** — does an IP work while a name fails? Then look at DNS before touching anything else.
5. **Service layer** — if IP and name both work and the port answers, the problem may be the application or content, not the network.

That order is layers 1→3→name→service, and it is also the N5 troubleshooting method applied to a client. Use it every time until it is habit.
