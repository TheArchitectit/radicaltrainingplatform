# Troubleshooting (N5)

*Module N5 — CompTIA Network+ study track. Independent study material — see the disclaimer at the end.*

Something stops working. The difference between an hour of guessing and ten minutes of fixing is almost never talent — it is whether you follow a method. This lesson covers the repeatable troubleshooting method, how to tell the three fault families apart, and the small toolkit that turns symptoms into measurements.

## The method: identify, theorize, test, plan, verify, document

Network+ formalizes what good technicians already do instinctively into six steps:

1. **Identify the problem.** Gather information, question users, identify symptoms, determine what changed, duplicate the problem if you can, approach multiple problems one at a time.
2. **Establish a theory of probable cause.** Start with the obvious. Consider multiple approaches — top-to-bottom or bottom-to-top the stack, divide and conquer.
3. **Test the theory.** If the theory is confirmed, figure out the next step to resolve. If not, establish a new theory or escalate. Testing a theory is cheap; acting on a wrong one is not.
4. **Establish a plan of action** to resolve the problem, and identify its potential effects. A fix that breaks something else is not a fix.
5. **Verify full system functionality** and implement preventive measures if applicable.
6. **Document findings, actions, outcomes, and lessons learned.**

Two habits distinguish professionals from tinkerers inside this loop. First, **safe tests before invasive ones**: `ping` before a cable swap, a config re-read before a firmware update. Second, **isolate by halves**: with a chain of client → switch → router → server, test the middle. Each result eliminates half the remaining chain. The A+ troubleshooting module (A5) teaches this same loop for hardware; here it is applied to networks, and the two are deliberately the same discipline.

## The three fault families

Most network faults fall into one of three families, and the family determines the tools:

- **Physical faults** — cable damage, bad transceivers, wrong ports, power. The link light is the first witness: no light usually means the physical layer is not up at all.
- **Service faults** — the wiring is fine but a *service* is broken: DHCP not leasing, DNS not resolving, a time service wrong. These fail selectively — the link is up, some things work, the affected function does not.
- **Configuration faults** — everything is present but *wrong*: a bad gateway address, an incorrect VLAN assignment, a duplicate IP. Configuration faults are the most common and the most instructive, because the fix is often a single field.

## Performance symptoms vs. hard failures

A **hard failure** is binary: the ping replies or it does not, the page loads or it does not. A **performance symptom** is degraded but working: slow, intermittent, jittery. The distinction matters because they call for different responses — you *fix* a hard failure, but you first *measure* a performance symptom, because "slow" without a number is untestable. Latency (delay), packet loss, and jitter (variation in delay) are the three baseline measurements; the N3 module's monitoring lesson covers how baselines make "slow" meaningful.

## The diagnostic toolkit

Four tools cover the beginner's working set — each answers one question:

- **ping** — "is the destination reachable at all, and how long does a round trip take?" The first safe test for almost anything.
- **traceroute** — "where along the path does it stop?" Each hop that times out narrows the fault to a segment.
- **nslookup** — "is name resolution working, and what is it resolving *to*?" The DNS-specific tool; it distinguishes "no answer" from "an answer that is wrong."
- **ipconfig / ifconfig** — "what does this host *think* its configuration is?" The cheapest possible test: read the four settings (IP, mask, gateway, DNS) before theorizing about anything remote.

The pattern across all four: each turns an anecdote ("it's broken") into a measurement ("it stops answering after hop 3"), and measurements are what the method's test-theory step actually consumes.
