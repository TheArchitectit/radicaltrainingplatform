# Hardware Maintenance (S3.2)

*Module S3.2 — Nutanix NCA 7.5 study track. Independent study material — see the disclaimer at the end.*

Hardware fails. A disk wears out, a power supply dies, a node needs a memory upgrade. This lesson is about the operator-level workflow for dealing with that, and it has one central idea: **get the work off the hardware before you touch the hardware**. Everything else is the sequence around that idea.

## The one rule: evacuate first

The cluster is built so that no single node holds the only copy of anything. That property is what makes maintenance possible without downtime — but only if you use it.

**Evacuating** a node means asking the cluster to move that node's data and workloads elsewhere, so that the node can be taken out of service safely. While the node is evacuating, the cluster is rebuilding or relocating copies onto the remaining nodes. When it finishes, the node is holding nothing that only it has, and it can be powered off, opened, or removed.

Skipping this step is the classic beginner error. The node *looks* safe to pull because the cluster is healthy — and it is, right up until the moment you remove the copy of the data that was living on it.

## Disk failure: the workflow

A failed disk is the most common hardware event, and the workflow is short:

1. **The cluster notices.** A failed disk raises an alert, and the data that was on it is rebuilt from its other copies onto the remaining disks. This happens without intervention; your job is to confirm it happened, not to trigger it.
2. **Confirm the failure is real.** A disk can be reported as failed because of a transient fault. Before ordering a replacement, confirm the cluster agrees the disk is genuinely gone.
3. **Replace the disk.** Physical replacement is safe *because* the data was already rebuilt elsewhere — the cluster is not depending on the failed disk.
4. **Confirm the rebuild.** After the replacement, the cluster uses the new capacity and the state returns to healthy. Verify this rather than assuming it.

Note what is *not* in that list: there is no step where you copy data off the failed disk, and no step where you shut the cluster down. The design has already handled it.

## Node failure: the workflow

A node failure is the same idea at a larger scale, with one addition — the workloads that were running on the node.

- **If the node fails on its own**, the cluster restarts its virtual machines on the remaining nodes. There is a short interruption, because a running machine cannot be moved after the fact; it has to be started again elsewhere. Confirm the machines came back and that the data rebuilt.
- **If you are taking the node down deliberately**, you do it in the other order. First **evacuate** the node so its workloads migrate away with no interruption and its data moves to other nodes. Then, once the node is genuinely empty, take it out of service.

The distinction between those two paragraphs is the heart of this objective: an unplanned failure *restarts* workloads, a planned maintenance *migrates* them. Planned maintenance is what you do when you can, precisely because it is the version with no interruption.

## The ordered sequence for planned node maintenance

When a question asks for the correct order, this is the sequence it is testing:

1. **Confirm cluster health first.** Maintenance on an unhealthy cluster is how a small problem becomes a large one. If something else is already degraded, fix that before adding a failure.
2. **Evacuate the node.** Move its data and workloads away. Wait for this to complete — not merely to start.
3. **Confirm the node is empty.** The evacuation finishing is the signal that it is safe to proceed.
4. **Take the node out of service.** Now the physical work can happen.
5. **Return the node to service**, and confirm the cluster rebuilds onto it and returns to a healthy state.

Steps 2 and 3 are the ones people skip, and they are the ones the sequence exists to enforce. "I started the evacuation" is not the same as "the node is empty".

## Why the order matters

Every step in that sequence exists because of a specific way things go wrong:

- Maintenance on an already-degraded cluster means the next failure has no margin.
- Pulling a node before it is evacuated means removing a copy the cluster still needs.
- Leaving a node out of service without confirming its return means running at reduced capacity without noticing, so the *next* failure is worse than it should be.

The exam does not usually ask you to recite the steps. It gives you a situation and asks which action is correct *now* — and the answer is almost always the one that keeps the cluster's ability to survive a failure intact.
