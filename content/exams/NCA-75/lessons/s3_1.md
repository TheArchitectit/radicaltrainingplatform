# Valid Cluster Options (S3.1)

*Module S3.1 — Nutanix NCA 7.5 study track. Independent study material — see the disclaimer at the end.*

"Valid" is the key word in this objective. When you design or expand a cluster, some combinations of choices work and some do not, and the reason is always the same: the cluster has to be able to survive the failure it promises to survive. This lesson explains the decisions, the constraints behind them, and how to tell a valid option from one that merely looks affordable.

## Replication factor: the first decision

Section 2.3 introduced replication factor as a storage setting. Here it becomes a design decision, because it determines what the cluster can survive.

- **RF2** keeps two copies of the data, on two different nodes. It survives the loss of **one** node. It costs roughly twice the raw data in usable space.
- **RF3** keeps three copies, on three different nodes. It survives the loss of **two** nodes at once. It costs roughly three times the raw data.

The framing question is not "which is better" but "**how much failure must be survivable**". A cluster that promises to keep running when two nodes are lost must be built with RF3, and the capacity arithmetic must account for it. Choosing RF3 on a cluster whose capacity was sized for RF2 is a valid *setting* and an invalid *design* — the cluster will run, and it will fill up.

## The node-count constraint

The second constraint follows directly from the first, and this is where most invalid options are caught.

If data is kept on two different nodes, then losing one node leaves exactly one copy — and the cluster must be able to rebuild that copy onto a remaining node. That means there must be somewhere for it to go. With too few nodes, a failure leaves the cluster holding the only surviving copy of the data, with no room to rebuild and no margin for a second failure during the rebuild.

This is why the standard minimum is **three nodes** for RF2, and why RF3 arrangements want more nodes still. The rule is not arbitrary; it is "enough nodes that a failure can be absorbed and repaired".

So when you evaluate a proposed configuration, the check is mechanical:

1. How many nodes?
2. What replication factor?
3. If the promised number of nodes fails at once, is a complete copy still present, and is there a node left to rebuild onto?

An option that fails step 3 is invalid regardless of price.

## Node awareness and block awareness

The cluster also has to be careful *where* it puts the copies, because two nodes in the same chassis can fail together.

- **Node awareness** places copies on different nodes. This is the baseline: it protects against a single node failing.
- **Block awareness** places copies on nodes in different chassis. This protects against a whole block losing power or being removed for service.

The point is that node awareness alone is not enough if the nodes it chose share a chassis. A configuration that spreads copies across nodes but not across blocks is valid for a single-node failure and invalid for a block-level failure — so whether it is "valid" depends on what you promised the business it would survive.

## Two-node and stretched arrangements

The standard rules bend in two directions, and both are deliberate rather than exceptions to be avoided:

- A **two-node cluster** can be a valid design for a small site, but it has no majority of its own to decide who survives a failure. It is made valid by pairing it with a **Witness** — the tie-breaker from section 1.3. Without one, the design is incomplete.
- A **stretched cluster** spans two physical sites so that either site can carry the workloads. Its validity depends on the link between the sites and on an arbitration mechanism that prevents both sides from deciding independently that they are the survivor.

In both cases the pattern is the same: the arrangement is valid **because** something outside the pair provides the deciding vote. Remove that and you have an invalid design that will appear to work until the day it does not.

## Evaluating an expansion choice

Growing a cluster raises the same questions at a smaller scale:

- **Does the addition keep the failure guarantee?** Adding nodes does not automatically improve protection if the copies are not placed to use them.
- **Is the new capacity enough for the replication factor in use?** A cluster at RF3 needs a third more space per unit of data than the same cluster at RF2, and an expansion sized without that will be short.
- **Is the resulting configuration homogeneous enough to operate?** Mixing node types is normal, but it affects where workloads can run and where data can be placed, so it is a design consideration rather than a purely commercial one.

The exam framing is usually a choice between options where one is subtly impossible: too few nodes for the replication factor, copies that would land in the same chassis, or a two-node arrangement with no arbiter. Your job is to spot the impossibility and say why.
