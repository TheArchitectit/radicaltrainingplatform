# Virtual Machine Tasks (S2.1)

*Module S2.1 — Nutanix NCA 7.5 study track. Independent study material — see the disclaimer at the end.*

A virtual machine is the unit most people actually care about. This lesson covers the handful of things you do to one: create it, change it, copy it, move it, delete it — plus the two ideas that trip beginners up, console access and the difference between a snapshot and a backup.

## Creating a virtual machine

Creating a virtual machine means making decisions in a few groups, and it helps to know the groups before the screens:

- **Identity** — a name, and how many virtual processors and how much memory it gets.
- **Storage** — which disk image it boots from, and how much disk space it has. The disk lives in a storage container on the cluster, which section 2.3 covers.
- **Network** — which virtual network it attaches to. Section 2.2 covers this.
- **Startup behaviour** — whether it starts automatically when the cluster starts, and how it should shut down.

Beginners often treat the storage and network choices as plumbing to get past. They are not: a virtual machine with the wrong network attached is unreachable, and one with too little disk will fail later in a way that looks like an application problem.

## Changing a virtual machine

Some changes can be made while the machine is running and some cannot, and the distinction is worth internalising:

- **Memory, most processor settings, and network attachments** can usually be changed live, though some guest operating systems need a reboot to notice.
- **Disk size** can be increased while running in the usual case, but shrinking a disk is not something you do casually — you would create a new, smaller disk and copy the data instead.
- **The boot device** and similar fundamental settings generally want the machine stopped.

The general principle: the further a change is from the operating system's view of the hardware, the more likely it needs a restart.

## Cloning and templates

A **clone** is a copy of a virtual machine. Cloning saves you from reinstalling an operating system every time. A **template** is the same idea taken further: a prepared, generic image kept specifically for making new machines, often with a step that customises hostname and network settings so the copies do not collide.

Cloning is the right answer to "we need ten more of these". It is the wrong answer to "we need to preserve this machine exactly as it is today" — that is a snapshot.

## Migrating a virtual machine

**Migrating** moves a running virtual machine from one node to another without shutting it down. The machine's memory is copied to the destination node while it keeps running, and it is switched over at the end. In a healthy cluster this is routine and is what lets a node be taken out for maintenance with no downtime for the workloads on it.

Two things follow. First, migration needs both nodes to be able to reach the machine's storage, which is why shared storage is the foundation of live migration. Second, if a node fails *without* a graceful migration, the cluster can restart its virtual machines elsewhere — a different operation, with a short interruption, rather than a seamless move.

## Console access

A virtual machine's **console** is its screen and keyboard, delivered over the network. You use it when the machine is not reachable over the network — during installation, after a network misconfiguration, or when the guest is too unwell to accept a remote session.

That is the whole point of the console: it works when nothing else does, because it does not depend on the guest's networking. If a question says "the virtual machine does not respond on the network and we need to see what it is doing", the answer is the console.

## Snapshot versus backup

These two are confused constantly, and the distinction is a favourite exam topic.

- A **snapshot** records the state of a virtual machine's disk at a moment in time, on the same cluster. It is fast, it is cheap, and it is meant for short-term use: take one before a risky change, and remove it once the change is proven good.
- A **backup** is a copy of the data held somewhere separate from the cluster, so that losing the cluster does not lose the data. It is slower and it consumes its own storage, and it is meant for long-term retention.

The failure this distinction prevents: a snapshot is not a backup, because both the machine and its snapshots live on the same cluster. A cluster-wide failure takes the snapshots with it. Snapshots protect you from *a mistake*; backups protect you from *a loss*.

## Deleting a virtual machine

Deleting a machine removes it and its configuration. The question worth asking first is whether its snapshots and any dependent clones should go too — deleting a machine whose snapshot other machines were cloned from can leave those copies in an awkward state. The habit to build is: check what depends on the machine before you remove it.
