# Virtual Networking (S2.2)

*Module S2.2 — Nutanix NCA 7.5 study track. Independent study material — see the disclaimer at the end.*

When you created a virtual machine in the last lesson, you attached it to a virtual network and moved on. This lesson is about what you were choosing. Three ideas cover most of it: what a virtual network actually is, how VLANs keep traffic apart, and why some networks are managed while others are not.

## A virtual network is a label, and a bridge

On a Nutanix cluster, a **virtual network** is a named object that virtual machines attach to. It has two sides:

- On the **virtual side**, it is a name. A machine's network adapter points at it, and every machine attached to the same name can talk to every other one, as if they were plugged into the same switch.
- On the **physical side**, it is a bridge to the real network. The cluster carries the traffic out over its physical links, tagged so that the physical switches know which network it belongs to.

So "attach this machine to the production network" is shorthand for: give this machine an adapter, bind it to the object called production, and let the cluster tag and forward its traffic out to the physical fabric.

## VLANs: keeping traffic apart

A **VLAN (virtual LAN)** is how one physical network carries several logically separate networks. Each VLAN has an identifier — a number — and switches use that number to keep the traffic of one VLAN from leaking into another.

The reason it matters here is the ordinary one: your production machines and your test machines may sit on the same physical switches, but they must not be able to talk to each other by accident. Assigning them to different VLANs enforces that separation.

When you create a virtual network on the cluster, you normally give it the VLAN identifier that the physical switches already use for that segment. Get the number wrong and the machine is attached to the right cluster but the wrong network — it will be up, and it will be unreachable by the people who expect to reach it. This is one of the most common beginner mistakes, and it produces a symptom (machine running, network apparently fine, nobody can reach it) that is worth remembering.

## Managed and unmanaged networks

A cluster can create and track virtual networks itself, or you can point it at networks that were defined somewhere else. That is the **managed versus unmanaged** distinction.

- A **managed** network is created and maintained on the cluster. The cluster is the source of truth: you define it once and machines attach to it by name.
- An **unmanaged** network is one that already exists on the physical infrastructure, defined on the switches, and the cluster is told about it so that machines can be attached. The cluster is not the source of truth; the physical network is.

The practical consequence is where you go to change something. If a managed network's details are wrong, you fix them on the cluster. If an unmanaged network is wrong, fixing it on the cluster accomplishes nothing, because the cluster is only repeating what it was told.

## What changes for a virtual machine

When a network setting changes, ask what the machine *sees*, because that is what determines the symptom:

- **Attaching a machine to a different virtual network** changes which segment it is on. If the new segment has a different address range, the machine's own address becomes invalid and it will lose connectivity until its addressing is updated — by hand, or by the addressing service on the new segment.
- **Changing the VLAN identifier** behind a network moves every machine attached to it, at once. This is why a VLAN change is a change to be planned, not made casually during the day.
- **Adding a second adapter** gives the machine a presence on two networks at once. Useful when a machine genuinely has to straddle two segments, and a common source of confusion when it happens by accident, because the machine now has two addresses and the traffic may leave by either.

The general rule: the machine does not know it was moved. It keeps the address it had, and everything depends on whether that address still means something on the segment it now sits on.

## IP address management

Addresses have to come from somewhere. On a well-run network, a **DHCP** service hands them out automatically and the cluster is told where to find it, so that newly created machines get a valid address without anyone typing one in. Where addresses are assigned by hand instead, an address plan is kept, and the discipline is to record what you assigned.

The failure to recognise: two machines with the same address on the same segment. The symptom is intermittent and maddening — connectivity that works, then does not, then works — because which machine answers depends on timing. When you meet a symptom that flickers, duplicate addressing is worth ruling out early.
