# RadicalTrainingPlatform: full audit and change reconciliation

October 10, 2026. Read-only assessment of `TheArchitectit/radicaltrainingplatform`. Historical baseline: `2b17f518d0f88e081c6018e7246cbd81a1d494a5`, the commit reviewed on October 1. Current inspected main: `904106ad388c0d48add662ddcd02153ff5f85537`, dated October 5. This is an audit, not implementation. Proposed repairs describe work an executor would perform later; they are not changes made during this assessment.

## Executive judgment

The repository has made real progress since October 1. The newer desktop application is no longer fairly described as a collection of views backed by only Core tests. Dependency injection has a composition root and dedicated tests. The desktop has headless smoke tests. Statistics and export have concrete handlers rather than only presentational surfaces. The simulator bridge has real handlers and a JSON session store. Errata is now consumed by the question parser. The catalog's question counts and discovery behavior have received fixes, and encoding fixtures cover more than the original UTF-8 path. These changes matter because they turn previously missing wiring into inspectable code with a test surface.

That progress does not establish the product Roger now wants. A beginner A+ track, a beginner Network+ track and an updated Nutanix NCA track are not already present. The standalone Web tree still presents a Nutanix lab simulator rather than a complete multi-vendor lesson, practice and coaching system. The existing question bank is large, but its lint pass does not mean all questions are usable in the runtime, current, source-reviewed or legally suitable for redistribution and AI ingestion. An apparently blocking vulnerability gate has a parser defect that can report success without inspecting the actual scanner's package tree. The current NCA beta blueprint differs materially from the current official NCA guide. Several study surfaces contradict one another even after a content repair commit.

The correct delivery posture is therefore "build on repaired foundations, with explicit content and runtime gates", not "rewrite everything" and not "the bank is already certification-ready". Existing code should be retained where its contract is useful. New work should close identity, objective mapping, content eligibility, study persistence, Web learning and tutor boundaries with small tested increments. The October 23 demonstration can be a complete beginner learning loop without implying that all official objectives, hardware exercises or examination preparation are finished. The California milestone should use the current NCA 7.5 objectives and visibly reviewed scope rather than displaying a beta-era checklist as current.

## Reading this audit

The audit separates four evidence classes. **Observed code/content** means a named file, data record or Git diff was inspected at the pinned commit. **Executed check** means a command or isolated fixture actually ran and produced the recorded result. **External current evidence** means an official vendor source or live GitHub API result was read on October 10. **Unverified behavior** means an outcome still needs an installed-host, browser, real device, rights or subject-matter review. A file's presence is not an executed result. A workflow's green conclusion is not evidence that every intended assertion is sound. A practice question's explanation is not independent support for its answer key.

Findings are ranked by the consequence for the selected product. A high finding can block a trustworthy demo or mislead learners even when the application compiles. A medium finding can create a data, maintenance or coverage risk that should be fixed before a broader release. Low findings are cleanup and clarity work that do not outrank scoring, security or source integrity. Severity is not a claim about exploitability unless the report gives a reproducer and the relevant boundary. In particular, the vulnerability-gate bug is a verified fail-open logic defect; it does not establish that any currently referenced package has a known advisory.

The report also distinguishes the historical audit from its own successors. The October 1 PDF is a source for the earlier assessment, not an authority that overrides current code. Its recommendation not to merge an old audit branch cannot simply be copied forward after that branch's findings have entered main. The current state of the merged tree is what must be reviewed. Likewise, the earlier broad "no persistence" label must be narrowed. Simulator JSON persistence exists now; durable learner attempts and history require their own proof. The user's selected tracks resolve one product question from the older platform plan, but do not automatically resolve AI provider, paid activation, content licensing or deployment choices.

## User goal and boundary

Roger selected all three basic certification tracks after discussing an AI presentation for high school students. The intended teaching point is practical AI-assisted building and learning, connected to IT work rather than only game development. The track feature is part of that demonstration and a later Nutanix visit. The expanded request calls for a full audit since the previous audit, an additional gap analysis and a full OpenSpec package, with substantial minimum lengths. This audit supplies the first part and evidence for the next two. It does not enroll students, buy exam vouchers, sign up a model provider, contact certification bodies, publish course material or modify a GitHub branch.

The distinction between preparation and release is important. A private planning document can describe a corpus intake process without redistributing that corpus. A local content inventory can identify a question's wording without passing the whole bank to a model provider. A sample fixture can expose a broken gate without turning it into an instruction to weaken CI. A demonstration can show a general networking lesson without promising official certification approval. The planned product must keep these distinctions in its interface and implementation, not leave them only in this report.

### Desktop repair and headless checks

The interval aligns Avalonia packages to 12.1.3. That addresses the earlier mixed-version finding in the inspected project file. It adds a headless desktop test project, smoke paths for the main window and blueprint data pipeline, review-button crash repairs, global exception handling, export wiring and real statistics. These repairs reduce the likelihood that an application which merely builds will fail immediately when a learner clicks review. They also improve the ability to catch future manifest and new-track errors through the real application composition instead of only testing detached Core functions.

The remaining audit boundary is host behavior. Headless Avalonia checks do not establish that the embedded Chromium engine launches on the presentation machine, that projector text is readable, that keyboard focus enters and exits the lab predictably or that the learner can recover after a storage failure. Those should become explicit rehearsal evidence, not assumed benefits of the new smoke suite. A current passing test can only be credited to the assertions it actually makes. The runtime evidence chapters supplied with this report name the tests and limitations rather than treating all desktop UI behavior as covered.

### Catalog and parser repair

The catalog's question count is now derived with a multiline header regex. The exam repository rejects markdown without question headers instead of accepting unrelated project documents as zero-question examinations. `RegisterSearchPath` permits callers to prepend content directories, and encoding fixes normalize line endings and remove BOM characters before parsing. These are meaningful improvements for a future pack compiler or lesson distribution route. They reduce incidental failures when content comes from files with different transport or editor conventions.

However, the catalog and parser still perform different jobs with different normalization. The catalog counts raw header matches, while the parser turns recognized blocks into scored questions only when it finds options and a valid key. Consequently, the catalog count can be larger than the usable runtime count. A displayed total should not be generated from headers alone once a track is intended for learners. It should come from validated released records and be reconciled with the runtime loader. A content build should fail rather than silently ship a pack in which catalog counts and runtime question counts disagree.

### Errata and study-text changes

The current parser can use an injected errata provider. `JsonErrataStore` searches near the executing assembly and upward through the directory tree, loads `answerKey` corrections and applies them to matching source-file/local-question keys. It logs malformed or unsupported entries and treats the absence of an errata file as nonfatal. This addresses the earlier finding that `errata.json` was inert. It also introduces a deployment dependency: the expected corrections must be delivered with the application or incorporated into validated pack output, not merely present in the development checkout.

A separate content correction commit changes the NCA gap-fill explanation of upgrade order and expands the Prism Central maximum-VM statement to distinguish scale-out from a single large instance. The cheatsheet receives those same two changes. That is progress in propagating a correction beyond an answer key. Yet the cheatsheet still states that CVM SSH is disabled by default, contradicting the bank's corrected SSH item and errata rationale. The existing doc-review report also contains conclusions whose confidence exceeds the evidence it quotes. The audit therefore credits the correction mechanism while keeping content authority and semantic consistency open.

### CI vulnerability changes

The earlier workflow used a vulnerability command followed by `|| true`, so the scanner could not block a build. The newer workflow calls a Python script intended to fail on unapproved vulnerable packages, and the allowlist has an explicit expiry column. This is an improvement in intent and surface. But the script parses the wrong JSON shape: it only iterates when the scanner output is a top-level list. The actual documented `dotnet` machine-readable output is a root object containing projects, frameworks and package arrays. A root object therefore bypasses the package loop and reaches a pass message.

This finding must be carried forward as a concrete new defect, not summarized as "gate fixed" because the diff removed `|| true`. An isolated fixture containing a high-severity package advisory reproduced the false pass. That fixture did not invoke a real SDK scanner, and it did not modify repository files. The real-output verification remains useful, but the logic defect is already visible and reproducible at the Python boundary. The repair should include output-version pinning, schema checks and deliberate failure on unknown or incomplete scanner output. A security gate cannot treat a parser mismatch as a clean bill of health.

## Evidence limitations and what can be trusted now

The fastest way to misuse an audit is to convert its careful limits into a single readiness adjective. This assessment is useful because it identifies concrete boundaries: source inspected, commands executed, official objectives fetched, runtime evidence attached and remaining host/rights checks named. It is not a certificate of product safety or a warranty that every question is accurate. It is also not a legal opinion about vendor content. The absence of per-item rights records is a release gap that a qualified owner or reviewer must resolve; the audit must not invent a permission because a source is public.

The current CI run can be trusted as a reported success of a named workflow at a named SHA. Its individual job records show the intended build and smoke steps were successful. It cannot be trusted as independent proof that the vulnerability gate parses advisories correctly. The content lint can be trusted as a header/answer-prefix count check at the pinned tree. It cannot be trusted as parser parity, ordered-response support, answer correctness or current-objective coverage. The official NCA guide can be trusted for its present exam structure and product versions, while legacy URL fragments and leftover training copy are kept as source inconsistencies rather than quietly blended.

For the new scope, the most valuable early acceptance artifact is a small completed loop with trusted content. It should have an explicit exam/lesson version, stable item identity, a reviewed key, deterministic scoring, a repeatable synthetic scenario and a resettable learner state. A tutor can be added only after its evidence and policy boundary is defined. More modules or more questions do not compensate for missing identity or invalid scoring. The audit's purpose is to make those dependencies visible before implementation time is consumed on a large but misleading catalog.


# Content, assessment and current certification alignment

## Content audit method

The content audit begins with the records RTP actually has, not with the size of the future catalog. The current bank has 22 root markdown files. Each file uses question headings, lettered options and an answer line, with prose explanations following. The audit ran `python3 scripts/lint-content.py` at the pinned checkout and received `OK: 22 files checked, 1598 questions validated`. It also counted headers independently and inspected answer-line syntax, per-file key distributions, local IDs and selected semantic conflicts. The word "validated" in the linter's output is the program's own label. This report interprets it according to the code's actual checks: counts of question headers and accepted answer prefixes, plus empty-answer detection. It is not a correctness certification.

This method intentionally does not use an LLM's agreement as evidence that an answer is right. The README describes multi-model validation and a blueprint gap pass. Those are statements about the project's process, not independently audited item records. A valid content process needs a traceable source, a precise claim, an objective and version, a reviewer decision and a license or permitted-use basis. Without those fields, an evaluator cannot distinguish an original exercise from a reconstructed exam question, or a current product behavior from a remembered beta fact. The gap is documentary as well as technical: the current Question model has no place to store most of that evidence.

A useful audit also distinguishes item syntax from assessment design. A parser can produce a question object whose answer is technically representable but pedagogically wrong. A multi-select scorer can accept a set of letters even when the author intended an order. An explanation can exist but contradict the key, contain an overconfident operational rule or refer to a deployment model absent from the stem. A source URL can exist but point to an entire manual without identifying the relevant section. The new tracks need all of these checks. Making the linter stricter is necessary, but it is not a substitute for review.

## Finding C-01: catalog and runtime disagree on accepted answer syntax

**Priority:** high for trustworthy assessment. **Evidence:** `NCP-AI-Part4.md`, questions 61 through 70, and `RadicalTrainingPlatform.Core/Services/QuestionParser.cs`, `AnswerRegex` and the parsed-question inclusion condition. The content file uses answer lines such as `**Answer: B and D**`. The production regex permits letters A-F separated by commas or whitespace, followed by the closing bold marker. It does not permit the word `and`. The linter's `VALID_ANSWER` expression matches only the beginning of the answer line, so it accepts these records. Header and answer-prefix counts remain equal even though the runtime parser cannot recognize the complete key.

The consequence is more than a ten-item discrepancy. The catalog counts the headers and advertises the larger bank. The parser requires at least one option and at least one recognized answer before adding a Question. A learner can therefore see a catalog count that describes authoring text rather than available practice. If objective coverage is calculated from a different representation, it may credit records the learner can never encounter. If an export loads parsed questions, it can silently omit them. The same weakness can recur in future A+ or Network+ packs if authors adopt natural conjunction wording or copy a style from the existing bank.

The ten affected line references are directly observable: answer lines at 805, 819, 833, 847, 861, 875, 889, 903, 917 and 931 in the inspected file. An independent Python translation of the production regex rejected those answer strings while the repository's linter passed the entire bank. The runtime verification should confirm the C# parser counts against the same files and record the exact parsed totals. The audit does not confuse a translated regex check with actual .NET execution; they are separate evidence classes. The static defect remains clear because the unsupported letters in `and` cannot fit the anchored grammar.

The repair has two plausible designs. One is to standardize authoring on a canonical grammar such as comma-separated uppercase letters and fail the content build on every other form. The other is to explicitly support a small number of alternative forms through a shared parser contract. Either can work, but the linter and production parser must consume the same validated representation or run parity fixtures. It is unsafe to add another loosely permissive regex that counts answers without validating options, duplicate letters, item type and exact syntax. The canonical compiled pack should report all rejected records and block release rather than allowing a silent drop.

The regression set should include the current ten records as fixtures, a comma-separated multi-select, a space-separated form if that remains supported, a malformed conjunction, an answer letter not among the options, repeated letters, a missing closing marker and a blank key. The catalog count should equal the number of released runtime records. A fixture with one invalid item should make the pack invalid, not reduce the displayed count while reporting a successful release. Existing progress identity must not change if a corrected item retains the same meaning and stable source ID; a materially changed item requires a new revision or explicit migration.

## Finding C-02: ordered answers are modeled as unordered selections

**Priority:** high for assessment integrity. **Evidence:** NCA gap-fill questions 16 through 19 contain ordering prompts and answer sequences. The Question model contains a list of correct letters but no explicit response type. `IsMultiSelect` is simply `CorrectAnswers.Count > 1`. The session view model stores selected answers in a HashSet and sorts both the correct key and the selection before comparing them. This is appropriate for an unordered set response, but it destroys the order needed by a sequence question. The response UI therefore cannot faithfully grade the exercise as written.

For example, NCA gap-fill Q17 asks the learner to place operations in order and has the key `D, C, B, A`. An unordered multi-select scorer treats selecting A, B, C and D as equivalent. The learner has not demonstrated the maintenance sequence. Q16 asks for a write-path order and Q18 asks for a storage hierarchy, with longer letter sequences. These prompts may look advanced, but their current runtime representation can reduce them to selecting every available option. Passing such an item can create confidence without testing the concept. The word "ordering" in an inline heading is only text, not a type contract.

The audit does not resolve the technical correctness of every sequence. Some ordering prompts require a subject-matter review in their own right. It isolates the representational defect: even a perfectly sourced sequence cannot be graded correctly with sorted set equality. The same issue would arise in an A+ troubleshooting procedure or a Network+ diagnosis workflow if a later author writes an ordered prompt into the existing multi-select shape. The new track spec must not assume that putting an ordered key in markdown creates a supported question type.

A safe immediate disposition is to quarantine ordering records from scored packs until an ordered response type is implemented, or convert them into original single-choice questions whose options are whole sequences. Conversion is not a mechanical parser operation; it changes the exercise and needs reviewer approval. A full ordered-response implementation needs explicit type, list length, allowed tokens, complete ordering, optional partial-credit policy and a keyboard-accessible interaction. The correct sequence should be compared position by position. A HashSet is not an appropriate storage type for the ordered learner response. Multi-select behavior must remain unchanged for true set questions.

The regression set should include two permutations containing exactly the same letters, with only the intended permutation passing. It should also include a missing step, a duplicate step, an extra token, empty response, reversed order and a correct order with a neutral display shuffle. If the UI randomizes option presentation, it must keep stable semantic IDs rather than grading visible letter positions that change between views. The test should confirm that retry, review, export and progress migration all preserve the response type. A content compiler should reject an ordering item if the selected host does not support that type, rather than downgrading it to multi-select.

## Finding C-03: severe answer-position bias weakens practice validity

**Priority:** medium for a private demonstration, high before readiness claims. **Evidence:** independent per-file key distribution over the root banks. `NCP-AI-Part1.md` has 80 single-answer records and all 80 have A as the key. `NCP-AI-Part2.md` has 79 A keys out of 80. `NCM-MCI-Part1.md` has 79 A keys out of 80. `NCP-CI-Part2.md` has 79 A keys out of 80. Other files are heavily B-biased, including 30 of 40 NCA Part 2 records. These are authoring observations, not a statistical estimate of learners' future behavior.

A learner can discover a position pattern and improve apparent accuracy without learning the material. Randomizing the order of questions does not remove that pattern because the option positions remain fixed. A time-limited session can therefore reward clicking a favored letter rather than reasoning through the distractors. The problem is especially visible when one entire file uses one answer letter. Such a distribution does not itself prove that the keys are wrong; it shows that the assessment presentation has an avoidable shortcut. The review process should make this shortcut measurable and remove it before using scores as a learning signal.

The repair should distinguish authoring quality from presentation shuffling. A balanced authoring bank is easier to inspect, but arbitrary forced balancing can also create patterns or damage distractor logic. The application can shuffle options through stable option IDs where the question's meaning allows it. However, options such as "all of the above", letter-referential wording or ordering tasks cannot be shuffled blindly. Keys must reference semantic IDs, not the newly displayed letter. A seeded test should show that a question remains correct after several permutations and that review and export display the learner's actual presentation accurately.

The content pipeline should report answer-position distributions at file, module and pack levels, plus flags for unusually concentrated patterns. The report is a review aid, not an automatic reason to rewrite keys. Human reviewers should inspect whether many superficially similar questions were generated from a template, whether distractors are implausible, whether the correct option is consistently longer or more detailed and whether explanations reveal the answer before submission. Removing position bias does not cure weak distractors or factual errors. It simply closes one visible route by which a learner can score well without showing the intended knowledge.

For the beginner demo, the safest scoring message is "you completed this practice task" or "you answered these reviewed questions", not a percent probability of passing a certification exam. Small banks and repeatedly exposed items cannot provide a valid readiness estimate. A future holdout test needs independent items and an explicit assessment design. The OpenSpec should define scores as practice feedback, with objective evidence and exposure count, rather than implying that a sample of twenty questions can stand in for the official examination. This distinction protects both the learner and Roger's credibility.

## Finding C-04: the NCA beta map is no longer the current objective map

**Priority:** high for the California track. **Evidence:** the current official NCA page and the June 15, 2026 NCA 7.5 blueprint guide fetched on October 10, compared with `HardcodedBlueprintService.cs`, NCA markdown headings and `CHEATSHEET-NCA-75.md`. The current guide has four sections: recognizing solutions and tools; describing platform administration; describing cluster configuration and maintenance; understanding platform health and monitoring. It contains fourteen numbered objectives. The repository's NCA blueprint starts with lifecycle management and assigns different topics to the same numeric objective labels.

This is not merely a title change. If progress is keyed only by `1.1`, a learner's historical attempt may be shown against a new objective with a different meaning. If keyword coverage continues to use the old map, the interface can show reassuring coverage for a section the official guide no longer defines that way. If a tutor retrieves using the old objective label, it can explain a relevant Nutanix concept while answering the wrong curriculum question. Version identity must therefore be part of every mapping and progress claim. Renaming a section in place is not enough.

The current guide identifies AOS 7.5, AHV 11.0 and Prism Central pc.7.5 as the tested software versions. The certification page's URL still contains `v6-10`, and one training paragraph in the guide also refers to NCA 6.10. The audit preserves these source inconsistencies. The page body and guide heading clearly identify the current NCA 7.5 target, so the old URL fragment should not drive the new curriculum. A source record should store the visible title, version, retrieval date and relevant objective locator. The pack's official display name should be NCA 7.5 exam preparation for NCA 7 certification, not an invented NCA-75 public credential name.

A remapping inventory should process all 140 NCA records. Each item needs its original file/local ID, current semantic version, old domain, proposed current objective, exact supporting source, reviewer decision and eligibility. Some records can retain their identity while gaining a current mapping. Others may be out of scope, beta-specific, ambiguous or unsupported. Those should remain in a quarantined historical corpus rather than appear as current practice. The process must not insist on reusing every record simply because the bank exists. A smaller reviewed current slice is more useful than a large bank with false objective labels.

The current guide's sections do not provide the same kind of domain percentage table used by CompTIA. The preliminary proposal of ten reviewed pilot items per section is a study allocation, not an official NCA weight. The interface and export should say that explicitly. A source-grounded curriculum may distribute more lessons to administration because it has four objectives, but it must not fabricate examination weighting from lesson length or bank size. Objective coverage should mean that a reviewer has mapped at least one eligible learning/assessment record to an objective, not that a keyword appeared somewhere in a question.

## Finding C-05: keyword coverage is not curriculum coverage

**Priority:** high if the product displays zero gaps or readiness. **Evidence:** `HardcodedBlueprintService.CalculateCoverage()` and `GetObjectivesForQuestion()`. For each objective, the current service checks whether any configured keyword appears in a question text, case-insensitively. Every matching keyword contributes a count for that objective. This provides a rough discovery aid, but it cannot determine whether the question actually tests the objective, whether the explanation is right, whether the current version applies or whether a learner has mastered the task. The implementation's own comment describes it as question matching, not a reviewed mapping.

The failure modes are straightforward. A distractor can contain the keyword without the correct response testing that concept. An explanation can mention several products and inflate multiple objective counts. Common terms such as network or VM can match widely. A negated statement still contains the token. A question can test a specialized detail while missing the objective's core skill. Conversely, a well-written question can use a synonym or scenario description that contains none of the selected keywords. A zero count therefore means "no keyword hit", while a positive count means "some text matched", not reliable coverage.

The correct place for keyword matching is an authoring recommendation: propose candidate mappings for a reviewer. The released pack should contain explicit objective IDs with the official exam version. The compiler should verify that the objective exists and that the mapping was reviewed. It should report unmatched objectives, lesson coverage, question coverage and practical-task coverage separately. A knowledge question does not substitute for a hands-on task where the curriculum expects operational skill. The UI should show the basis of each coverage metric rather than collapse all evidence into a green percentage.

A migration from keyword mapping can preserve existing content without silently upgrading its confidence. Historical records can be marked `mappingStatus: inferred` until reviewed. New records should not enter released scored practice with only an inferred map. A test fixture should include a distractor mentioning the keyword, a negated claim, a synonym-only stem and a record whose objective was removed in a new blueprint revision. The compiler should not reinterpret past progress under the new map. It should provide a review report that explains why an objective is incomplete and which eligible records support the displayed count.

This is especially important for the three-track plan because A+ and Network+ share concepts at different depths. A DNS lesson can appear in both tracks, but its curriculum relationship must be explicit. The A+ task may ask a support technician to inspect a workstation configuration. The Network+ task may ask for diagnosis in a topology and verification of external routing. Counting one generic networking question in both tracks does not establish independent coverage or independent assessment evidence. Shared lesson components should have their own IDs, while each exam mapping and scored item retains its specific objective and depth.

## Finding C-06: corrected content still contradicts its companion surface

**Priority:** high for a tutor corpus, medium for manual study. **Evidence:** `errata.json`, NCA gap-fill Q3 and `studyguides/CHEATSHEET-NCA-75.md`. The errata rationale and the corrected question say SSH remains enabled by default for the stated fresh-install case. The cheatsheet's AOS 7.5 changes list still says SSH is disabled by default. This audit treats the contradiction as verified. It does not independently establish the vendor default from the repository's own report because that report is not a source-of-truth statement from Nutanix.

The distinction matters. It would be tempting to declare one side definitively right because a prior author accepted a correction. The doc-review report quotes workflows that assume SSH is available, then infers a default and a deferred product change. Operational examples do not necessarily prove every fresh-install default. A full correctness review needs the precise current vendor source, release version and applicable configuration condition. Until that source is found, the pack should not turn either side into an authoritative tutor answer. The verified audit finding is that RTP's study surfaces disagree and its correction process did not close the loop.

The same pattern appears in the maximum-VM correction. The doc-review report acknowledges that the downloaded manuals do not contain the Configuration Maximums annex. It then recommends 25,000 for scale-out and marks the summary confidence high. The stem's exact deployment model and current vendor limit must be checked against the configuration-maximums source before a scored item is released. The newer text distinguishes a single large VM from a three-VM scale-out deployment, which is a better-shaped claim, but a better-shaped claim still needs evidence. An errata field pointing to an internal report is not equivalent to a current vendor citation.

A correction workflow should update the scored key, explanation, cheatsheet, reference card, tutor source and generated export from one canonical record. It should also keep the evidence and reviewer attached. A semantic consistency test can search for known retired phrases and ensure they no longer appear in released surfaces, but it cannot replace review. The test should explicitly cover the SSH statement, the deployment qualifier for maximum VMs and any global upgrade-order claim. If the product needs to preserve a historical beta cheatsheet, it should be labeled historical and excluded from current retrieval rather than edited silently into a mixed-version document.

## Finding C-07: beta-era exam logistics are stale

**Priority:** medium for the California demonstration, high if learners use the material to schedule an examination. **Evidence:** the NCA cheatsheet still has a Beta Exam Tips section, a waiver code, a beta period ending June 14, 2026 and a result-wait statement. The current date is October 10. Those logistics cannot be offered as current without live vendor confirmation. The current official guide describes a production NCA 7.5 exam and NCA 7 credential. The correction is simple in concept but must respect identity. A current pack should link to the vendor scheduling page and show the source review date. A historical beta pack can retain its records with an obvious status and no current scheduling call to action. A current learner should not be shown an old voucher code simply because it appears in a markdown cheatsheet. The same rule applies to fees, duration, passing scales and recertification periods. The audit should not copy every logistics number into the new spec when the demo does not need them.

Exam logistics also intersect with the beginner audience. The official A+ page recommends twelve months of hands-on support experience. The official Network+ page recommends A+-level knowledge and nine to twelve months of relevant experience. The NCA page describes approximately three to six months of infrastructure and equivalent Nutanix experience. The presentation can say the tracks offer a beginning path, but it should not promise that no-experience learners will be exam-ready after a few short lessons. ## Finding C-08: content identity is too narrow for a multi-vendor release

**Priority:** high for preserving progress. **Evidence:** the current Question model stores integer local ID, exam code, domain string, stem, options, correct letters, explanation and source file. The session key combines exam code, source file and local ID. That is a useful improvement over a bare integer because local IDs restart across files. It still lacks pack version, item revision, objective version and release eligibility. The model cannot tell whether a question's meaning changed between content updates or whether a remapped objective should affect historical progress.

Filename-derived exam identity is another boundary. `DeriveExamCode` strips part suffixes and then returns a limited segment form for several patterns. Codes proposed for new packs can collide or be truncated if passed through that heuristic without a manifest override. The vendor map recognizes prefixes such as A, N and Sec for CompTIA, but a new explicit `COMPTIA-A-1201` name would not automatically have the expected vendor metadata. Unknown level defaults are professional, which is misleading for beginner packs. Display metadata must therefore be explicit rather than inferred from a filename convention never tested with the new scope.

A versioned manifest should define stable vendor, track, exam and pack identities; official code and display name; objective-source version and review date; language; content revision; supported response types; released item IDs; and applicable licensing status. The learner store should reference semantic item identity and revision. An update that only fixes punctuation can retain learning history. A changed answer, scope or operational meaning should show that prior attempts were on an earlier revision. Deleted items should remain as retired historical references, not be reassigned to a different question number. Migration tests should make this behavior visible.

This is not an argument to replace all markdown immediately. Markdown can remain the authoring format if a compiler produces explicit validated records. Existing source-file/local IDs can be preserved as legacy origin identifiers. The new structured contract should not be a second competing scoring engine. It should supply identity and metadata to the existing tested learning seam, then support both desktop and Web consumption. A small pilot containing one A+ core, one Network+ lesson and a reviewed NCA slice can prove the contract before the whole bank is migrated. The compiler's counts should become the public counts.

## Finding C-09: content and source licensing remain unresolved

**Priority:** high before distribution or AI ingestion. **Evidence:** README claims BSD-3-Clause and links to a root LICENSE file; no root LICENSE was found in the inspected tree. The repository contains two vendor PDFs under docs. The bank and cheatsheets contain substantive technical text but lack per-item rights records. The audit cannot determine ownership or permission from these facts alone. It does not claim the bank is a dump, and it does not claim vendor PDFs are unlawfully distributed. It identifies missing evidence needed to make a safe release decision.

A code license, an original-content license, a third-party manual license and an exam-material policy are different things. Adding a BSD license to Roger's code would not license Nutanix manuals or CompTIA exam questions. A public URL permits reading a source; it does not automatically permit bundling, embedding, redistribution or transmission to an AI provider. Likewise, a disclaimer saying the tool is unaffiliated does not resolve source provenance. The intake process should record separate rights for display, distribution, indexing and provider transmission. If a source is linking-only, the course can point to it without copying it into the pack or retrieval index.

Existing vendor PDFs should be inventoried with title, version, owner/publisher, source URL, hash and license or permission record. Their current tracked presence is a repository fact, not a release decision. The audit does not remove files, rewrite history or choose a license. A later authorized executor should handle those actions under a documented owner decision and keep destructive cleanup separate from ordinary pack building. For the demo, the simplest safe plan is original reviewed lessons and links to official sources, with uncertain manuals excluded from the model corpus. That avoids turning an unresolved rights question into a hidden dependency for October 23.

Original questions need provenance too. The author should attest that an item was written from public learning objectives and technical knowledge, not reconstructed from live or remembered examination content. A reviewer should look for suspicious near-duplicates or claims of actual examination questions. Similarity checks can help locate risk but cannot prove legality. A record that claims to be actual, leaked or recalled exam content should be quarantined. The current audit found quality problems and weak evidence; it did not investigate or make a finding of deliberate exam compromise. The language in the package must maintain that distinction.

## Finding C-10: current CompTIA AI policy changes the tutor plan

**Priority:** high before presenting AI as certification assistance. **Evidence:** CompTIA's unauthorized-training-materials page fetched on October 10. The page says CompTIA does not authorize or condone AI, LLMs or similar tools generating study questions, practice exams or exam-related content. It warns that AI-generated questions or answers may be inaccurate or substantially similar to unauthorized examination content and that candidates remain responsible for using legitimate preparation sources. This is broader than a generic "human review before publication" rule. The new specification must not assume human review alone makes AI-generated CompTIA exam practice endorsed or acceptable.

Roger challenged any claim that this policy legally prohibits independent AI-generated teaching content and selected a clear disclaimer that RTP is neither official nor endorsed training material. The audit preserves that direction. It does not render a legal verdict, claim the policy is a statute, or treat a disclaimer as permission to copy actual examination content. The specification can cover original AI-assisted authoring with human review, provenance and exam-integrity checks, while recording the vendor policy as a separate candidate-facing risk. Any uncertain rights or policy interpretation needs a defined review task, not a categorical legal assurance. The demonstration should be framed as general IT-skills coaching rather than an official practice-exam generator.

A recorded tutor example can demonstrate interaction design without pretending to be a live model. It should be labeled recorded and use a general troubleshooting concept. A live tutor, if later permitted, should receive only approved lesson context, not the entire bank or vendor PDFs. It should have no exam-time overlay, no ability to reconstruct likely examination questions and no access to hidden answer keys during assessment. The interface should distinguish general learning help from preparation assessments. The source policy should be linked in the administrative decision record so a future editor does not silently reintroduce forbidden authoring behavior.

Nutanix's candidate agreement has its own restrictions on copying, reconstructing and distributing actual examination content. The audit fetched the agreement as a source for the exam-integrity boundary. It does not treat the agreement as a blanket ban on all original technical teaching, and it does not infer that every public blueprint reference is freely redistributable. The content intake process should keep vendor-specific policy records rather than flatten all vendors into one generic AI permission. A multi-vendor platform requires per-vendor and per-source eligibility because the same feature can be acceptable in one curriculum context and unresolved in another.

## Content acceptance gate proposed from the findings

A released scored pack should require explicit IDs, current objective mappings, supported response type, valid options/key, reviewed explanation, provenance and eligibility. A malformed record should fail compilation. Counts should be derived from released records, not raw headers. All hashes and versions should be available in a release manifest. The same pack should be loadable in the selected host without reaching back into a repository directory. A clean-machine fixture should show that the lesson, question, correction and source card remain available with the intended network conditions.

The quality review should include factual correctness, ambiguity, distractor plausibility, position bias, deployment qualifiers, version scope and exam-integrity screening. Reviewers should not approve a question merely because several models produced the same answer. Conflicting sources should produce a hold or a revised stem, not an averaged conclusion. Any maximum, default or procedural sequence needs the exact applicable source condition. A content correction should propagate to every derived surface and create regression evidence. The bank's size becomes useful only after these checks make it trustworthy.

The learning UI should distinguish exploration from exam preparation, practice scores from certification readiness and general AI coaching from exam-related generation. It should show incomplete coverage. It should link to official vendor sources for logistics without bundling unsupported material. It should keep historical beta packs visibly historical and exclude them from current retrieval. Learner progress should preserve the version of the item actually attempted. A content update should not rewrite a learner's past into success on a different question or objective.

These gates are not bureaucratic decoration. They directly answer the failures observed in RTP: malformed keys that pass lint, ordering graded as a set, stale objective numbers, contradictory text and missing rights records. The implementation work should map each gate to a test, a reviewer record and a released artifact. If a proposed task cannot name its evidence, it is still a plan. The gap analysis and OpenSpec should use this audit to prioritize those exact boundaries before expanding the three tracks into a broad product promise.

## Finding CI-01: the nominal blocking vulnerability gate fails open

The script `.github/scripts/vuln_gate.py` was introduced to replace a scanner invocation that ended with `|| true`. It accepts project paths, runs `dotnet list <project> package --vulnerable --include-transitive --format json`, loads the output as JSON and compares package records with an expiry-based allowlist. This is a sensible intended boundary: scanner failure, malformed output or an unapproved advisory should stop the build. The implementation, however, iterates only if the JSON root is a list. The documented and real scanner output is an object with `projects`, each containing `frameworks`, and each framework containing `topLevelPackages` and possibly `transitivePackages`.

When the root is an object, the script's expression produces an empty iterable. No package records are visited, the hit count remains zero and the script prints that no vulnerable packages exist. It then prints `VULN GATE: PASS`. An isolated fixture in this audit contained a high-severity advisory under the real object shape and reproduced the false pass. A separate runtime verification pass then confirmed the same behavior against actual SDK scanner output from a scratch project using Newtonsoft.Json 12.0.1. The scanner reported advisory GHSA-5crp-9r3c-p9vr, while the repository script printed no vulnerabilities and returned exit zero. The current Desktop scan reported no vulnerabilities, so the finding is the false guarantee, not an allegation about the current package set.

The machine-readable output contract is documented by Microsoft at https://learn.microsoft.com/en-us/dotnet/core/tools/dotnet-package-list and the NuGet specification at https://github.com/NuGet/Home/wiki/%5BSpec%5D-Machine-readable-output-for-dotnet-list-package. Both sources were fetched. The runtime verification pass also observed lowercase `advisoryurl` in the actual advisory record. A repair should not merely adjust one loop and assume every future SDK shape remains compatible. It should pin an output version, validate the root and expected traversal, normalize documented advisory fields and fail on unknown shapes. The absence of recognized packages must be distinguishable from a valid report that contains no vulnerable packages.

The allowlist also needs a tested contract. Package and resolved-version matching should be case-consistent with NuGet identity. Expiry dates should be parsed deliberately, invalid dates should produce a configuration error, and missing expiry should never become an indefinite exception. Every exception should identify its justification and approved scope. A scanner process failure or unparseable response should remain blocking. A configuration file with a missing header, extra unknown fields or duplicate conflicting entries should not silently create a broader exception. These are proposed test requirements, not repairs made during this audit.

The minimum regression suite should include a real-shaped clean report, a top-level vulnerable package, a transitive vulnerable package, multiple projects/frameworks, an empty valid project, malformed JSON, an unknown root version, scanner exit failure, an expired exception, a matching current exception, a wrong-version exception and a malformed expiry. A high-advisory fixture must return nonzero and name the affected package. A clean fixture should pass only after the schema was recognized. The gate should save a compact structured evidence record with SDK version, output format, project set and timestamp so a future audit can tell what was actually inspected.

## Finding CI-02: collected coverage is not an enforced coverage threshold

The Linux workflow collects XPlat code coverage during Core tests. No explicit threshold enforcement step appears in the inspected workflow. Collection and enforcement are different. A coverage file can be generated while a new module has no relevant tests. A repository claim of a minimum percentage is not evidence that the build will fail below it. Coverage also measures execution, not correctness: the conjunction parser defect can survive if the test suite never uses that exact content syntax, and a bridge test can assert a hardcoded value without proving a real persistence flow.

The repair should establish a declared threshold and a report path, then test the gate itself. An executor should choose whether the threshold applies to the whole Core package, changed files or critical components, with a rationale. Critical scoring, identity migration, storage failure, content parsing and security-gate boundaries need direct behavioral tests regardless of a package average. A test-only fixture below the threshold should demonstrate failure in CI. An excluded generated file should be identified explicitly rather than disappearing from coverage unnoticed. Desktop smoke results should remain a separate measure because they do not fit the same line-coverage interpretation.

The new tracks create a natural opportunity to add a content/runtime parity suite. It should compile all released authoring records, load them through the actual runtime contract and compare counts, IDs, keys, types and objective mappings. Every current malformed-key example should fail the authoring gate or parse into a valid reviewed record after correction. This parity suite would have caught the ten conjunction keys that passed the existing linter. It should run independently of content size and should report the exact file/local ID for a failure. A large bank is no excuse for a silent skip.

## Finding CI-03: Pages deployment has no learning or simulator smoke gate

The Pages workflow publishes the `RadicalTrainingPlatform.Web/` directory when files under that path change. It uploads static files and deploys them without an import-resolution check, browser smoke or scenario validation test. The audit worker found a missing static import that prevents the application graph from booting. That defect was present at the earlier baseline and remained deployable because the workflow did not exercise the startup contract. A deploy pipeline can therefore complete successfully while publishing an empty shell.

The repair should add a predeployment build or module-graph validation step and a browser smoke that opens the built artifact, waits for a known route, checks console errors and verifies a meaningful interaction. An import checker must verify all relative module paths with case sensitivity appropriate to the deploy host. The browser check should run without relying on the source checkout, mock host transport or previously cached assets. The service worker should be disabled for a first-load smoke and then tested separately for update behavior. That separation prevents a cached good version from masking a broken candidate or a cached bad version from confusing a repaired candidate.

The future Web study pack must be included in the artifact deliberately. Root markdown banks are outside the current Pages path. A new content compiler should generate eligible JSON into a defined artifact directory and a manifest should reference its hashes. The deploy gate should verify every manifest asset exists, no forbidden or unreviewed corpus is bundled, no provider key appears in assets and the offline cache contains the intended minimum lessons. An artifact-size or source count check can help, but the decisive evidence is a clean-browser lesson and question load from the built directory. The same build should have a release identifier visible in the UI.

The workflow builds the newer desktop project on Linux and the whole solution on Windows. A source file describing macOS packaging does not create a tested macOS support claim. ## Packaging and installability

The repository contains Linux AppImage and macOS DMG scripts plus Flatpak metadata. These files are useful starting points, but they are not released bundles. The live GitHub API returned zero releases and zero tags. The desktop fallback points users toward a release location where no bundle currently exists. That mismatch creates user work: the user or learner has to discover that the download path is empty. The interface should not offer a completed download route until a real release artifact exists and its link is validated. A development-mode message should explain the limitation without promising a package.

### Finding PKG-01: content delivery depends on source-tree assumptions

The exam repository searches current directory, executing assembly directory, application data and parent directories. That supports development layouts and registered search paths. It can also make a development build appear successful because bank files are found in the repository root, while an installed bundle has none. The desktop project explicitly copies simulator Web assets, but the current packaging paths need an inventory proving which question banks, errata, manifests, lessons and licenses are included. The audit should not assume that a copied simulator directory includes the study content.

The repair is a deterministic content bundle contract. The build should include only released packs and their metadata, then use a defined installed content location. A clean directory test should run the application with no repository parent and confirm a known exam, count, question, correction and lesson are available. A missing content directory should produce an actionable error, not an empty catalog that looks like successful startup. Additional user-installed packs should use registered paths or an import mechanism with validation, not arbitrary directory walking that can pick up unintended markdown. The same test should show that a malformed pack is rejected without replacing the working one.

### Finding PKG-02: the AppImage fallback is not actually a fallback when the tool is missing

The Linux script publishes a self-contained application, prepares an AppDir and then invokes `appimagetool`. If `appimagetool` is absent, it prints an error and exits one. The later tarball fallback step therefore never runs in that condition, despite a comment saying the fallback works even without the tool. This is a source-proven control-flow defect. It does not require a Linux packaging run to see that an earlier exit prevents the later command. The intended outcome should be specified: either fail strictly without an AppImage, or produce a clearly labeled tarball fallback before returning an appropriate status.

The regression should use a controlled PATH with `appimagetool` unavailable and verify the intended output exists, has an executable launcher and carries the same content manifest. A separate path should exercise a successful AppImage tool. Failed publication, missing icons or missing native libraries should not produce a "Build complete" message. A bundle validation script should inspect expected files and launch from outside the repository. This turns the packaging script from a recipe into an evidence-producing release step.

### Finding PKG-03: the macOS script's label exceeds its guaranteed output

The macOS script says it builds a signed and notarized DMG, while signing and notarization are optional environment-controlled steps. It defaults to osx-arm64 despite a comment mentioning a universal binary. If `create-dmg` is missing, it creates a ZIP fallback and exits successfully. These behaviors can be reasonable, but the resulting artifact should carry an honest status: architecture, signed/unsigned, notarized/not notarized and DMG/ZIP. A future release should not describe every output as signed and notarized merely because that phrase appears in a script comment.

The repair should validate required credentials through secure build configuration, never place them in documents or logs, and record the actual signing/notarization result. A macOS smoke should launch the bundle on the selected architecture and verify content and embedded-browser behavior. A universal claim requires an actual universal build and inspection of the binaries, not a comment. The fallback should be tested and its user-visible installation instructions should match the artifact type. This is a release-truth requirement rather than a demand to sign anything during the audit.

### Finding PKG-04: Flatpak metadata has stale and inconsistent execution assumptions

The Flatpak file pins a short historical commit and includes comments asking for predownloaded NuGet sources. Its output path is `/app/bin/RadicalTrainingPlatform.Core`, while the wrapper executes that path directly. In a typical publish layout, an output directory contains the application executable; the wrapper needs to identify the actual binary rather than treat a directory as an executable. The audit marks this as a source-level packaging concern requiring a real Flatpak build and install test. It does not claim the package has been executed or approved for a store.

The repair should pin the intended full SHA or release tag, declare complete sources and use a verified launcher path. Permissions such as home-directory access and network sharing should be reviewed against the actual learning and AI requirements rather than inherited wholesale. Offline packaging should have a reproducible dependency source inventory. A sandbox smoke should open a lesson and scenario, persist permitted local data, export where allowed and report a denied filesystem path clearly. The user should not need broad home access merely to study a bundled lesson if a narrower sandbox contract suffices.

## 4. NET-02, High: ordering is graded as unordered multi-select

NCA-75-Part3-GapFill Q17 explicitly asks for an LCM sequence and gives D,C,B,A. Q16/Q18/Q19 also require order. Models/Question.cs:12 treats all multiple-letter keys as multi-select. ExamSessionViewModel.cs:16 stores selected answers in HashSet. IsCorrect at :63-64 and Submit at :104 sort both sides before equality. There is no question kind preserving sequence semantics.

A runtime probe parsed the real file with production QuestionParser, selected Q17, and constructed the production VM. Expected key printed D,C,B,A. The probe selected A,B,C,D. Submit returned True and IsCorrect was True. The reverse sequence was accepted because comparison erased order. This is not a hypothetical interpretation or only a misleading label; it is a reproduced wrong grade on actual content.

For sequence items whose answer includes all offered letters, selecting everything can satisfy the set equality without demonstrating order. The educational contract is lost even when explanation text is correct. This can teach an incorrect operational sequence as correct, warranting High severity. More vendors/content would spread the same failure until the model distinguishes ordered and unordered responses.

Introduce an explicit kind, preserve ordered user input, and compare lists for ordering. Genuine multi-select must retain set comparison. Parse the type from an explicit source/schema field. Add an ordering interaction rather than toggle cards alone. Tests should include correct/reverse sequences containing identical letters, partial sequences, duplicates, and multi-select chosen in another order. Until implemented, excluding these items from automatic scoring is safer than reporting false correctness.

## 5. NET-03, Medium: retry outcome sets can contradict each other

Submit adds a question key to the correct or wrong set but never removes it from the opposite set. Navigation/JumpTo calls ResetState, clearing submitted/selection state so the question can be answered again. The relevant paths are ExamSessionViewModel.cs:99-126, :129-147, and :182-194. Decide whether grade means first attempt, latest attempt, or all attempts. First attempt should retain an immutable initial result with later practice separate. Latest attempt should replace prior outcome. All attempts require attempt records, not sets of unique question keys pretending to count attempts. Tests must cover both retry directions, skips, revisiting without submission, review membership, and the invariant that unique answered items do not exceed total questions.

## 7. NET-05, Medium: real storage is not desktop study resumption

The store has positive properties worth retaining. Session IDs containing slash, backslash, colon, or period are rejected. Save/Load/Has/Delete/List lock through the same object. Raw progress JSON is wrapped as a JSON string and unwrapped, preserving text exactly. List sorts IDs, and the default provider writes under application data instead of source directories. Tests and the real bridge round-trip prove those component operations work. Describing session persistence as wholly absent would now be wrong.

The missing connection is from actual study state to the new store. ExamSessionViewModel receives questions, code, and optional limit. It has no injected store, persistence schema, snapshot method, or restore constructor. MainWindow creates new VMs and never saves them. Targeted searches found no ISessionStore reference in these classes on main or advertised branches. Therefore closing the desktop app does not acquire study resumption simply because ISessionStore is registered in DI. A service registration is capability plumbing, not a user workflow.

Browser simulator persistence is another system. Its StateStore.js uses IndexedDB with localStorage fallback. Searching the bundled Web tree found bridge.post('ready') in app.js and no normal save_progress/load_progress call. The host handlers are reachable in tests or from a future caller, not presently used to save browser state through the usual UI. This review does not claim browser persistence is absent; it distinguishes it from the .NET session files. IndexedDB may preserve simulator entities while the study VM remains memory-only and host session files remain unused.

A completion plan should define a versioned session schema, stable question identity, question index, selected answers, scoring policy, optional attempts, and timestamps. Separate snapshot/save/restore responsibilities from visible views. Add autosave at deliberate points and a restored-session UI. Define how reset affects disk history and browser state. Test closing/reopening, switching modes, moving through Stats/Blueprint, version changes, and missing/corrupt files. That is the acceptance scope required before claiming a learner can stop carrying their study progress.

It is useful to close two tickets separately: storage engine implemented versus desktop resumption integrated. Combining them into one checkbox hides the real progress and the real gap. The bridge tests are good unit/integration evidence for the engine but are not an end-user resume test. A browser datastore and a host datastore can each round-trip perfectly while no shared definition of a session connects them.

### NET-12: durability hardening remains untested

SessionStore.cs:48-67 writes directly to the destination file, then deserializes its content on load. DefaultFileProvider delegates to File.WriteAllText. There is no temporary-file replacement, checksum/version envelope, backup recovery, or corrupted-file handling. Same-instance locks prevent concurrent operations in that store but do not make an overwrite atomic across process interruption and do not coordinate multiple application processes.

This is a source-supported hardening risk, not a reproduced data-loss incident. No disk failure, kill-during-write, truncated-file recovery, or multi-process test was run. The right recommendation is to implement atomic replacement and safe recovery before promising durability, then fault-test it. Do not report that a specific user's progress has been lost. A tested normal round-trip answers whether the code can write/read healthy data, not whether it preserves old valid data after a failed overwrite.

IDs are also validated by a small denylist rather than a platform-complete allowed format. Current traversal checks are useful, but Windows reserved names and other invalid filename characters can still reach filesystem errors. This was not separately reproduced on Windows and should remain a hardening note. A constrained ID scheme such as internally generated opaque IDs would reduce that cross-platform surface. Avoid expanding the finding into an unsupported claim of arbitrary filesystem access; path separators and traversal periods are currently rejected.

No memory-leak benchmark or harmful stale-callback scenario was reproduced here, so this is an implementation cleanup concern rather than another counted confirmed defect. ## 9. NET-07, Medium: disposed simulator instance is cached for reuse

MainWindow.axaml.cs:127-128 disposes a lab control when navigating away. It does not clear _labView. The next simulator click reaches :364, whose null-coalescing assignment reuses that nonnull object. LabSimulatorView.OnLoaded at :54 refuses startup when _disposed is true. LabSimulatorView comments correctly explain that visual-tree removal should not shut down a process-wide CEF runtime. Removing its Unloaded-to-Dispose subscription was meant to avoid that problem, but MainWindow still disposes the control on the same navigation event. The two classes' lifetime decisions disagree. Preventing duplicate dispose does not restore a browser after the cached object has been disposed once.

A headless UI probe attempted native opening. CEF loaded far enough to report native startup warnings, then exited because no X server/$DISPLAY was available. Thus this review does not claim a native second-visit blank screen was observed. The source path is deterministic, while native revisit and shutdown acceptance remain unverified. The passing thirteen-test repository suite does not exercise this opening path and cannot certify it.

Choose one ownership policy. Either keep the live control through navigation without disposing it, or dispose it and clear the cache so the next visit creates a new control. Coordinate shutdown explicitly. MainWindow lacks a window-close lab-disposal hook in the inspected source. Do not insert speculative direct CefRuntime.Shutdown/Initialize calls without checking the wrapper package's ownership. Absence of an explicit Initialize call is not itself reported as a bug, because CefGlue wrappers can initialize internally.

The native test failure is also a warning against describing the fallback as universally noncrashing. Managed catch blocks cannot necessarily intercept a native library terminating the process. This was an audit-environment missing-display case, not an end-user supported platform failure. A native acceptance environment should test first load, missing runtime, failed startup, tab leave/return, and window close with supported runtime/display conditions.

## 10. NET-08, Medium: EXAM:number cannot uniquely address current questions

The real get_question handler documents keys like NCA-75:12 and returns the first numeric match. CefBridge.cs:302-320 performs that lookup.
