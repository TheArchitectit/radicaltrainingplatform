## Decision

**NO-GO on live AI for the October 23 demo. GO on the recorded-example
fallback.**

This is not a finding of a failing evaluation — the evaluation passes
206/206 — it is that the *preconditions* REQ-AI-07 names for live AI are
unresolved, which is exactly the trigger REQ-AI-07 defines:

| Precondition (REQ-AI-07) | State |
|---|---|
| Provider / model chosen | **Unresolved.** No provider key exists in this repository and no model has been selected. |
| Transmission rights | **Unresolved.** The corpus index excludes all three vendor-objective packs for exactly this reason (`excluded vendor-objectives:… no provider-transmission right`). Transmitting lesson text to a third-party provider has no recorded right. |
| Cost posture | **Unresolved.** Dollar limits and any paid activation are owner decisions (G-05). |

REQ-AI-06's own remedy clause — *"Failing cases are fixed or live AI is
disabled for the demo"* — is not what forces this; the evaluation does not
fail. What forces it is that a live-AI demo would need a provider, a
transmission right and a cost decision that no one has made. Disabling live AI
is the honest state, and the fallback is what the demo shows.

## Fallback labeling — verified (REQ-AI-07)

REQ-AI-07's scenario is *"Given the fallback build, when the tutor panel opens,
then the 'recorded example' label is visible and no network call fires."*
Both halves are asserted, not assumed:

- `tests/gates/web/tutor-panel.mjs` — part of `run_web_fixtures.sh`, green:
  with no gateway configured the panel's mode pill reads exactly
  `recorded example` and carries the `recorded` class; the settings text reads
  *"recorded examples only"*; the default mode is `recorded`; each response
  carries the label `recorded example`; and **answering makes zero network
  calls** — the fixture counts every attempt to leave the page and fails on any.
- `tests/gates/tutor-eval.mjs` (`tm67-recorded-mode`) — the recorded path fires
  no network call, is labelled `recorded example`, and reports mode `recorded`.
- `tests/gates/tutor-eval.mjs` (`req-ai-05`) — with the gateway unreachable the
  tutor reports itself unavailable without inventing output, and the non-AI
  flows lose nothing.

The fallback therefore never presents itself as a live model: the label is
visible before use, and the panel is structurally incapable of reaching a
provider in this build.

## What this decision does not cover

- **Live model behaviour.** Nothing in the evaluation exercises a real
  provider, because none is activated. The gates are proven to *fail* against
  scripted and deliberately misbehaving responders; that proves the gates work,
  not that a model would pass them. This is the main reason the no-go is
  cheap: there is no evidence a live model would behave, only evidence that
  the pipeline around it would catch misbehaviour.
- **Human source review.** The packs are `draft`; no response carries a
  `sourceReviewDate`. The recorded examples are reviewed as *content*, not
  yet as *sourced*.
- **Real-browser rendering of the panel.** Covered by the web fixture suite and
  the T-22 smoke, not by this record.
- **The actual demo host.** Same block as S47-10: the host is undecided in the
  package (PKG:1469), so the panel has not been opened on the demo machine.
